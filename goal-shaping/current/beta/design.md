# loom-oi beta：当前设计共识

本文记录已确认的产品方向及已核对的跨会话共识，不代表代码现状、已交付能力或验收结果。候选方案见[活跃草稿](../../drafts/beta/first-flow/design.md)，讨论来源与演进见[沟通笔记](../../drafts/beta/first-flow/notes.md)。

## 目的与范围

让分散在不同机器、应用和设备上的功能可以被 Agent、脚本或其他程序发现、选中并使用，同时保留提供方的控制权。

beta 从头定义产品。alpha 用于理解原始意图，不自动继承其职责划分、实现和技术方案。先明确目标、概念和首个完整流程，再设计、实现和验证。本期不做独立消费端 oi。

首版只实现 Bash 作为能力接入 App，不实现 computer-use，保持 OIS 定义、OIC 接入与 App 业务实现的解耦。当前版本采用固定调用链：Agent → vMCP → Tool → Action → 通道 → OIC → oiapp → 对应目标 cmd。中间按配置直接转交，不增加多 Host 路由、同 Tool 多目标合并、动态选路或负载均衡。

## 核心概念

| 概念 | 含义 |
| --- | --- |
| Host | 提供受控功能的宿主机；宿主机统一使用 Host 命名 |
| App | 一组相关 Action 的组织与接入单位，由一份 YAML 描述，例如 bash、computer-use |
| Action | App 中具体可调用的操作，例如 exec、click、screenshot |
| vMCP | 面向消费者的 MCP 入口，将选定 Action 映射成 Tool，并组成工具集 |
| 通道 | 固定调用链中承接 Action 调用、到达对应 OIC 的通信环节；具体标识与协议仍待设计 |

App 包含 Action，Host 承载 App。Host 仍表示实际宿主机，但首版不作为 Agent 需要发现、选择的路由参数。Tool 已固定绑定目标 Action 及其通道，执行位置随绑定确定；这不要求整个系统只能存在一个 OIC。

Tool 是 OIS 面向 MCP 消费者配置的操作呈现；执行侧的 App、Action 标识与消费侧的 Tool 展示名称分开。原先用于宿主机的 Node 名称不再使用。未来如引入负载池或逻辑路由目标，需要另行定义，不再用 Node 混指宿主机。

## OIC 与 App 描述

OIC 保留为轻量 CLI 宿主，负责受控侧接入，加载 App YAML，识别本机提供的 App、Actions、参数 Schema 及相应执行配置。收到 OIS 转发的数据后，OIC 根据已加载的 YAML 识别目标 Action、处理参数并转发到目标 oiapp 的实现。接入已有应用也是统一接入模型的变体。

一个 App 一份 YAML，配套 actions 目录保存执行脚本。computer-use 的 click、screenshot 等操作属于同一个 App；bash、browser-use、wechat 等可以分别有自己的 App 描述。具体目录名、字段、脚本入口格式和打包规范尚未冻结。

App YAML 需要包含 Action 和参数 Schema 的基本信息，以及 Action 与实际执行入口的对应关系。OIS 维护面向消费者的 Tool 定义和描述，本地 Schema 描述接入实现所需的参数；两者不要求严格一致。“轻量适配”不表示省略本地参数声明，也不意味着将业务实现写进 YAML。

Action 采用以名字为键的映射结构；省略 handler 时默认使用 Action 名，需要不同入口名时再显式声明 handler。省略同名 handler 不等于省略 Action 的参数 Schema；具体字段与 Schema 支持范围仍待细化。

runtime 可以配置在 App 根节点，也可以配置在某个 Action 内。根节点提供默认执行配置，Action 上更具体的配置优先。只有 Action 级配置也应能表达该入口；配置合并粒度、具体载体与进程复用方式仍需设计。

项目统一接入和调用方式，各 Action 仍可接受不同参数。OIC 根据 Action 的参数 Schema 与有效 runtime 对接实际执行入口，执行时进行必要的参数适配；具体传输、输入输出、脚本启动和控制契约仍需设计。

OIC 是否采用常驻后台、是否按调用启动脚本、是否支持常驻执行器和如何取消或回收资源，尚未确定；App 不被定义为必须存在一个独立常驻协议进程。

## OIS 与消费侧映射

OIS 提供 API，管理 MCP 转换和工具组合。首版配置 Tool 对应的 Action 及其固定通道，并把 Tool 组成 vMCP。一次调用沿既有绑定转交到对应 OIC，不从多个执行目标中作选择。

OIC 提供 Action、参数 Schema 及执行入口的本地接入，不负责组装 MCP。OIS 维护工具定义、参数描述、展示信息和 vMCP 组合；本地 Schema 的存在不意味着 OIS 必须由它自动生成或覆盖 Tool 定义。执行侧根据 YAML 承接调用，不将两侧参数定义完全一致作为加载或组合的前提。

一个 vMCP 可以包含多个 Tool，每个 Tool 都有自己的确定绑定。多个 Tool 的组合不意味着单个 Tool 同时映射多个可选执行目标。一个 MCP Server 与一个 App 没有固定一一对应要求。

## 参数映射与执行时适配

加载时不强制检查本地参数与 OIS 工具定义是否匹配；发现可识别的差异时至多警告，不以这种差异阻止加载。YAML 可读取、执行映射可解析等基础要求与跨层参数匹配是不同问题。

真正调用时才根据实际入口所需参数做轻量匹配和序列化、反序列化，尽可能适配传递。可转换的字符串与整数不应只因类型不同而被拒绝；实际无法适配的结构，例如对象或数组没有可用映射却要求作为整数输入，应返回参数错误。JSON 是承载格式，这里的结构不匹配指实际值，不是所有 JSON 编码的值都不能转换为整数。

系统不承担复杂的跨 Schema 一致性验证，也不借适配增加大量业务校验。本地参数 Schema 提供基本目标类型信息，具体支持的 Schema 字段、转换范围、参数改名和错误形式仍需设计；方向是按调用作最小适配，而不是强制两侧定义完全一致。

## 首版固定绑定与调用参数

Agent 选择 vMCP 暴露的 Tool，直接提供业务参数；不再查询目标列表或传入 host_id、通道 ID 选择执行位置。OIS 根据 Tool 已绑定的 Action 和通道转发，通道到达对应 OIC，再交给 oiapp 的实现执行。

首版不实现同一 Tool 多 Host 合并、list_targets、允许目标列表、自动切换目标或额外调度层。此前多 Host 的讨论保留为后续背景，不再作为本版实现与验收要求。

中间环节只承担这条调用链所需的定义查找、连接转交、既有的轻量参数适配、结果返回与必要错误处理，不增加业务编排或自动重执行逻辑。具体工具参数封装和通道配置字段仍待设计。

## OIS—OIC 连接与执行边界

OIC 主动连接配置的 OIS。首版只通过既定的在线通道投递，通道不可用则返回错误，不切换到其他 OIC，也不积压离线调用等待恢复后突然执行。重连后重新登记能力；具体传输、存活检测和通道标识仍待设计。

既有接入权限与本地执行范围保留：OIS 管消费方能使用哪些已配置 Tool，OIC 只执行本机已加载、启用的 Action；本地停用后拒绝新调用。普通业务参数不能覆盖固定通道、执行入口、本机配置或接入凭据。首版不为此增加 Host 选择或复杂策略层，具体凭据及授权字段尚未冻结。

## 首版 Bash 的交互模型

Bash 按当前助手可见的 exec_command / write_stdin 命令工具交互方式设计，以两个 Action 作为核心接入：

- exec_command 启动一次执行并等待一段时间；已结束则返回输出和退出码，仍在运行则返回已有输出及 session_id，供后续继续操作。
- write_stdin 使用该 session_id；chars 为空时等待并获取后续输出，非空时写入输入并继续获取输出，直到执行结束。

这个方向采用等待窗口、输出预算和可选终端模式。yield_time_ms 表示本次等待时间，不是执行超时；max_output_tokens 表示本次返回输出的预算。具体默认值、上下限、预算估算方式及本项目最终字段格式仍需细化。执行程序由 Bash App 的本地配置确定，不因参考通用命令工具而允许覆盖任意入口。

session_id 标识同一次持续执行；新的 exec_command 不自动继承上次 shell 的目录或变量。同一存活的交互 shell 可以通过后续输入继续操作。该 ID 与原 App 实例及访问者范围关联；两个 Bash Tool 配置为到达同一执行后端，后续 write_stdin 沿固定绑定接续，Agent 不再重复选择 Host。

采用接口与可观察行为，不据此推定 Codex 内部的进程管理、缓存或持久化实现。首版核心不要求额外的 read、cancel、list、resize 工具或对外输出游标。中断输入与可靠停止、强制回收、断连恢复及结果保留规则仍需明确，不把发送控制字符视为已确认停止。

## 后续 Computer-use 的控制范围

CU 不属于首版实现范围。后续首个 CU 场景限定同一桌面同一时段只有一个控制者，控制范围覆盖截图、操作和再次观察。仅对单个 Action 排队不足以保证整个操作过程不被其他 Agent 干扰。

桌面上下文标识与控制权分别表达；占用、释放和控制者失联后的处理规则仍需设计，不从单控制者方向推定已经确定通用会话或工作流机制。

## 没有独立实体 Host 的接入

App 描述层仍需保留。如果接入对象只是一组远程 HTTP 接口、没有独立受控机器，对应 YAML 可以放在 OIS。

这确定的是统一 App 描述及其可放置位置，不代表已经设计 OIS 执行器、通用 HTTP 适配字段、凭据管理或具体执行部署。完整 MCP 接入、单 Action 接入及多受控方组合也使用统一描述和映射思路，具体适配方式尚未确定。

## 工作方式与 Done

开发及设计文档使用 beta 分支的独立 worktree；main、alpha 和历史实验 worktree 保留，alpha 的未提交改动不修改或删除。

SDK、Go、Rust、混合实现和具体传输都未定案。用户对目标讨论的授权不等于开始实现、提交或发布。

完整 Done 尚未形成。需要明确 App 准备与加载、Action 登记、OIS Tool/vMCP 固定绑定、Agent 接入、既定通道转交、实际执行与结果核对，以及失败处理的完整场景。

## 尚未确定

- OIS 工具定义、App YAML 的 Action/参数 Schema 字段、runtime 继承与覆盖细节，以及 App 与各 Host 上实例的标识方式。
- Action 脚本的输入、输出、错误、非文本结果、取消和执行环境契约。
- OIC CLI 与后台形态、加载/卸载、持续会话、恢复与资源管理；CU 控制权的占用、释放和失联规则。
- 执行时参数映射及轻量转换的具体规则、固定通道标识与接入授权实现。
- 调用状态、断连结果、重复投递及取消语义；在线即时投递之外的调用生命周期尚未确定。
- 后续是否增加多 Host 合并或负载均衡；首版已明确不做。
- 无独立 Host 的 App 在 OIS 一侧如何接入与执行。
- 首个支持的客户端、执行平台、Bash 两动作的具体字段与限额、交付形式及完整验收标准。

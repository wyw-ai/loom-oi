# OIC/OIS：从功能需求比较 Go 与 Rust

2026-11-02 · [#8](https://github.com/wyw-ai/loom-oi/issues/8)。回应用户 [评论](https://github.com/wyw-ai/loom-oi/issues/8#issuecomment-6561546252)。**语言未选定；以下官方事实与 AI 工程推导分开，没有项目性能实测。** 架构输入以 [整体方案](alpha-solution-design.md#packages) 为准，1C1G 是 OIC 所在机器规格，不是 OIC 可占满 1GB 的预算。

## 1. 先确定需要实现什么

| 功能 | A/R 基线必须做的工作 | 扩展如何改变判断 |
| --- | --- | --- |
| OIS 登记、发现、策略、路由 | 元数据与并发状态、认证、持久化边界、可诊断错误 | 规模/HA 尚未明确，不能先用“高性能控制面”定语言 |
| OIC 常驻接入 | 凭证、重连退避、配置 revision、健康新鲜度 | 如需嵌入其他进程，ABI/runtime 足迹成为新约束；目前没有这项要求 |
| 通道转发 | 双向 I/O、TLS、每流/全局有界缓冲、慢消费者、断开清理 | QUIC/多路径或统一适配要额外核对具体依赖，而非用语言声誉替代 |
| 能力服务 | 当前外部运行，原生协议与资源状态归服务 | 不能因为桌面服务需要 OS 绑定就断言 OIC 也必须大量 FFI |
| 发布与维护 | 目标系统、升级包、日志、故障定位、维护者能力 | 目标 OS/CPU 和团队熟悉程度尚缺资料；Loom 的语言不构成强制依赖 |

## 2. 语言特性如何影响这些功能

| 维度 | Go：事实与局限 | Rust：事实与局限 | 对 loom-oi 的推导 |
| --- | --- | --- | --- |
| 内存 | GC 管理堆；GOMEMLIMIT 为软限制且不含所有进程/外部内存 [G1/G2] | 所有权/drop 管理资源，不依赖追踪式 GC [R1]；仍有堆、分配器、缓存与泄漏风险 | 两者都必须限定流数/缓冲；不能把软限制或无 GC 当 RSS 上限。低内存/尾延迟压力需实测 |
| 长连接并发 | goroutine 由 runtime 调度 [G3]；共享状态仍需同步 | Tokio task/future，跨线程任务受 Send 等约束 [R2/R3] | Go 可用 goroutine+有界 channel；Rust 可用 task+有界队列；语言都不自动限制任务数 |
| 取消与清理 | context 传递截止/取消信号，协作者响应 [G4] | select 丢弃未完成 future，需注意取消安全及外部任务 [R4] | 都要显式关闭/中止 I/O 并核查资源释放；本地取消不等于远端业务回滚 |
| 并发安全 | 官方 race detector 可检查运行到的数据竞争路径 [G5] | Send/Sync 与所有权为安全 Rust 的跨线程共享提供编译期约束 [R3] | Rust 的编译期约束有价值；两者仍可能死锁、逻辑竞态、错误鉴权和资源耗尽 |
| 跨平台依赖 | 纯 Go 与使用 cgo 的发布条件不同；cgo 交叉编译需要目标 C 工具链 [G6] | target 支持分级，编译/运行保证不同 [R5]；实际 TLS/OS 依赖仍须核对 | 不能承诺任意组合“单二进制零依赖”；选真实目标矩阵再做构建验证 |
| 开发和维护 | 标准并发模型与网络服务形态适合纳入控制/接入原型候选 | 所有权及异步生命周期可表达更严格的资源约束，也需熟悉相应模型 | 哪个更快交付取决于团队与库选择，当前未知；不能把一般偏好计成项目人日优势 |

## 3. 可比较的工程方案与当前建议

| 方案 | 具体安排 | 优势假设 | 代价与改选条件 |
| --- | --- | --- | --- |
| G 全 Go 核心 | OIS/OIC 共用协议类型；提供方通过协议接入；有界复制、集中生命周期管理 | A/R 主要是网络服务，单语言可以减少初期发布和排障组合 | GC/内存余量需验证；如果相同负载下预算/尾延迟不达标且无法通过限流/分配优化解决，改考虑 R |
| R 全 Rust 核心 | OIS/OIC 共用契约；异步任务显式所有权；有限池/队列，清楚的取消边界 | 如果资源回收可控性/性能约束或团队 Rust 熟悉程度突出，可能有优势 | 编译期约束不替代架构与运行验证；如果迭代/跨平台依赖成本显著，不能只为无 GC 承担它 |
| M OIS Go + OIC Rust | 以独立协议/兼容测试连接两组件 | 只有两者需求和实测差异足够大才值得 | 两套构建/依赖/排障、协议类型与兼容矩阵；当前没有证据支持首版承担这些成本 |

**当前建议**：先保持 G/R 同等候选，首版目标为一种核心语言；用 A/R 同一契约做最小对比。若必须决定先写哪个验证骨架，在“团队熟悉度相当、主要网络转发、无嵌入要求”的假设下，我倾向先 Go，再用 Rust 对照同一压力路径。这是验证顺序建议，不是语言采用决议，更不是 Go 已被证实更快或更轻。

如果团队已有可直接复用且不依赖 Loom 业务的 Rust 能力，或 OIC 存在明确紧张的内存/尾延迟门槛，先 Rust 同样合理。H1 取消了“为了适配 Loom 必须同语言”的推理路径；通过协议消费不强制同语言。

## 4. 同条件验证设计（尚未执行）

先确认目标 OS/CPU、1C1G 上其他进程占用、可用 OIC 预算和代表负载；不能先测再挑有利门槛。测试预算是提案，未批准完整双实现。用一个最小 OIS/模拟器和两份同功能 OIC 骨架，只比较会改变选型的路径。

| 测例 | 保持相同 | 记录与判定 |
| --- | --- | --- |
| 空闲/常驻登记 | TLS、身份检查、描述规模、日志级别 | RSS、CPU、线程/任务、包体/启动；比较实际常驻负担 |
| 短请求与长流 | 协议、加密、载荷、并发、缓存上限、运行环境 | 端到端 p50/p95/p99、吞吐、峰值 RSS/CPU；分别记录 OIS/OIC/服务 |
| 慢消费与超载 | 相同流/全局缓冲限额、拒绝策略 | 内存是否有界、控制消息延迟、拒绝行为；不能靠无限队列获得吞吐 |
| 断线/重连/取消 | 相同故障点、退避、超时、计数器服务 | 任务/句柄回收、重连峰值、是否重复业务字节；运行时取消模型的真实成本 |
| 构建/维护改动 | 固定依赖版本、目标平台、同一配置字段/错误路径改动 | 构建成功率、人工问题、review 与定位成本；不以代码行数当唯一效率 |

每种配置重复运行并记录波动、工具链与锁定依赖；release 构建与同等优化，测试/诊断插桩开销另列。Go 可记录 GC 相关指标，Rust 可记录分配/任务指标，但最终比较同一端到端目标。当前没有可运行 OIC，不把网上微基准或 Hello World 当成本项目结论。

选择规则：正确性与目标环境先过门槛；只有一方满足已确认预算就优先它；双方都满足时按团队维护证据和依赖复杂度选择；都不满足先审视功能/队列/拓扑，不能默认混合语言就解决。门槛未确认或结果接近时保持 Pending，明确下一条有区分度的证据。

## 5. 一手来源（2026-11-02 核对）

- G1 [Go GC guide](https://go.dev/doc/gc-guide)：GC/CPU/内存权衡及软限制。
- G2 [runtime/debug SetMemoryLimit](https://pkg.go.dev/runtime/debug#SetMemoryLimit)：计算范围与外部内存局限。
- G3 [Go FAQ](https://go.dev/doc/faq#goroutines)：goroutine 的运行时调度。
- G4 [Go context](https://go.dev/blog/context)：取消信号与截止时间。
- G5 [Go race detector](https://go.dev/doc/articles/race_detector)：动态检测机制及运行覆盖局限。
- G6 [cgo 文档](https://go.dev/src/cmd/cgo/doc.go)：交叉编译的 C 工具链要求。
- R1 [Rust ownership](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)：所有权与 drop。
- R2 [Tokio spawning](https://tokio.rs/tokio/tutorial/spawning)：异步任务生命周期与 Send 要求。
- R3 [Rust Send/Sync](https://doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html)：跨线程安全约束及 unsafe 责任。
- R4 [Tokio select](https://tokio.rs/tokio/tutorial/select)：取消 future 的行为。
- R5 [Rust platform support](https://doc.rust-lang.org/rustc/platform-support.html)：目标平台支持分级。

这些资料证明语言机制，不证明项目性能、团队效率或架构胜负；相关推导必须同时引用上游功能范围。

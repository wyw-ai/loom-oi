# Issue 编写与维护规范

Issue是一个独立问题的当前评审入口。先读原件、最新正文/评论及关联规格，完成求解，再写正文；主类型、状态、评分帮助定位，不代替方案。文档职责见[结构规范](structure.md)，规格确认及实施门槛见[SDD](sdd/README.md)。

## 一单一个确认目标

标题写用户能力或具体取舍，保留`[alpha][Type]`，不放修订号。多个问题只有共享同一决定且不能分别收敛时才合并；关系用“类型＋目标＋理由”。同一目标更新现有单，不按每条聊天/每个测例建单。新探索主题由用户创建。治理本身是当前诉求时可独立建Governance单，不能用治理单代替产品方案。

## 正文固定六节

开头用两句话交代核心问题与推荐，随后一行元数据：Type、Topic、工作/成熟度/采用状态、优先级、I/U/N/E/C及成本范围。其余信息合并到以下六节，不逐字段各建一节。

| 二级标题 | 要回答的问题 | 原字段归位 |
| --- | --- | --- |
| 要解决的问题 | 谁在何场景遇到什么障碍，目标、范围及已有确认是什么？ | Context、Problem、Goal、Scope、Current Understanding |
| 当前方案 | 谁执行、输入/输出、状态归谁、正常与失败链如何走？ | Proposed Solutions、Recommendation、Walkthrough |
| 依据与取舍 | 哪条原话/证据支撑什么推论，合理替代、成本与推翻条件是什么？ | Evidence、Dependencies、Alternatives |
| 待确认项 | 少量可直接回答的选择及后果；哪些已经确认、不应重问？ | Open Questions、Decision Needed、确认范围 |
| 验证与完成条件 | 设计、采用、实验、实施分别完成到哪；缺什么、怎样判定？ | Validation、Acceptance Criteria、Progress |
| 关联 | 规格、来源、决议、验证和上游问题分别承接什么？ | Relations、DISC/需求/验证ID |

复杂方案可在“当前方案”下分三级标题。探索单在同一结构写价值假设、反证/停止条件；实施单写已确认输入、具体交付与验收；条件单写缺口→最小解阻→验证出口；治理单写实际失效→维护机制→迁移→检查。没有待确认项时说明准确范围，不凑审批。

## 原位更新与历史保真

每轮读取评论后将有效反馈合入上述六节，移除已被替代的推荐，不追加整块“本轮反馈”。保留原评论；历史方案用对应DISC基线/Git快照追溯，当前正文只留必要来源和明确决议。正文必须自足：不打开链接也能判断方案、一个失败例和主要取舍；细节可回链，不能成为链接目录或再次复制完整设计。

每轮讨论融合实际更新相关Issue供开发者确认；只有新独立目标才建单。不得擅自关闭、重开、指派、修改成员任务、合并或部署。已接受一个范围不等于整单完成；历史评论与当前正文冲突时回到明确原回复，并同步受影响规格/图/指纹。

## 分类与状态

| Type | 使用范围 | 标签建议 |
| --- | --- | --- |
| Product | 场景、体验、价值和范围 | `type:product` |
| Architecture | 对象、职责、边界和交互 | `type:architecture` |
| Technical | 协议、状态、算法与性能设计 | `type:technical` |
| Exploration | 有价值假设、反证及停止条件的新构想 | `type:exploration` |
| Decision | 充分方案已展开，需要明确人类取舍 | `type:decision` |
| Risk | 已发生缺陷或有触发/后果的潜在失效 | `type:risk` |
| Implementation | 依赖已确认、范围已授权的具体执行增量 | `type:implementation` |
| Governance | 工作方法、知识、模板与协作规范 | `type:governance` |


选一个主类型；未核验/配置标签时正文元数据生效，不声称标签不存在。本轮不改已有标签或成员字段。

工作状态：Triage / Designing / Review / Validating / Blocked / Implementing / Resolved / Deferred。方案成熟度：Sketch / Walkthrough / Experiment / Implemented。采用状态：Pending / Accepted / Rejected / Deferred；多范围分别记录。GitHub open/closed单独管理。

采用必须有明确原回复、作者/时间和准确范围；验证只按实际证据。`Review / Walkthrough / Pending`可提交，不代表实施获准；`Accepted`也不能替代实验门槛。结构检查通过不证明理解了用户原意。

## 轻量评分


I/U/N/E 使用1–5，C使用1–3；注明日期、评估者和理由，不确定写 TBD。本轮均为 AI 初评，非人员安排或最终选择。

| 指标 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- |
| Impact | 局部措辞 | 单个次要场景 | 单模块/主要场景 | 跨模块/多接入 | 核心边界、权限或副作用正确性 |
| Urgency | 以后可选 | 下一阶段 | 当前阶段后段 | 契约/验收前 | 当前核心范围/模型讨论前置 |
| Uncertainty | 已验证 | 少数边界未知 | 机制较明确但待实验 | 关键假设未测 | 多方案与机制均不清楚 |
| Effort | ≤0.5人日 | >0.5–1人日 | >1–3人日 | >3–7人日 | >7人日，需检查边界 |

C=1：主要推测；C=2：有可追溯原文/源码支持，具体方案未实测；C=3：有直接可重复的针对性运行证据。降低 N 不等于提升 C：机制更清楚了，仍可能未验证。

参考分 `S=2I+U+N`（4–20）帮助排列讨论，不自动决定优先级或选型。E/C 单列，不用复杂公式掩盖未知。E 明确估计后续设计验证或实现的哪一部分；本轮各主线的 E 仅指后续设计/实验验证，不含完整产品实现与采购。

P0=有证据的当前严重事故；P1=当前核心边界/正确性/契约前置；P2=有明确价值但可后续收敛；P3=认可但不紧迫。当前没有 P0，不因为存在潜在风险就标紧急。


## 提交检查

按[内容评审](../.agents/skills/discussion-sdd/references/content-review.md)检查来源保真、机制与反例；再检查六节、 typed关系、规格指纹与实验边界。保持正文更新、源文件更新和远端回读一致。模板在[问题与方案](../.github/ISSUE_TEMPLATE/problem.md)与[探索与决策](../.github/ISSUE_TEMPLATE/exploration-decision.md)；实时问题分工见[Issue导航](alpha-issues.md)。

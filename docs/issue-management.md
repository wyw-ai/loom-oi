# Issue 编写与维护规范

Issue是一个独立问题的持续讨论入口：初始正文保留问题快照，后续阶段通过追加记录演进。先读原件、正文、相关阶段评论及关联规格，完成求解，再发布增量；主类型、状态、评分帮助定位，不代替方案。文档职责见[结构规范](structure.md)，规格确认及实施门槛见[SDD](sdd/README.md)。

## 一单一个确认目标

先说明问题属于loom-oi的哪项用户结果/共同契约，再判断能否独立确认。会改变同一结果或成本前提的研究方向应作为同一主问题的方案维度；拆单依据共同验收和真实依赖，不能按组件名切断因果。按[项目收束规则](sdd/README.md#project-convergence)回写整体影响。

标题写用户能力或具体取舍，保留`[alpha][分类]`，不放修订号。多个问题只有共享同一决定且不能分别收敛时才合并；关系用“类型＋目标＋理由”。同一目标优先在现有单追加阶段评论，不按每条聊天/每个测例建单。新探索主题由用户创建。治理本身是当前诉求时可独立建治理单，不能用治理单代替产品方案。

## 中文显示与稳定标识

依据[#14回复](https://github.com/wyw-ai/loom-oi/issues/14#issuecomment-6596717601)，当前Issue标题、元数据、状态、分类和关系统一中文，八类沿用现有含义，先不增子类。当前活动单均无GitHub标签，暂以初始分类及明确阶段变更为依据，避免同时维护一套重复标签；以后确需平台筛选再统一迁移。

[词汇映射](vocabulary.json)供检查器与生成目录使用；JSON内部枚举、工具参数、历史原始证据和已有采用凭据保留稳定机器值。协议的Ready/NotReady/Unknown属于线上的具体语义，不能因治理中文化改协议。新正文解释为就绪/未就绪/未知，并在需要时保留代码名。

元数据采用“分类、主题、工作状态、成熟度、采用、优先级、评分”。混合范围用“部分已采用”，准确范围写在正文；验证状态单列。中文显示不改变open/closed、不扩展批准，也不把“已通过物料检查”写成“已通过实验”。

## 新Issue正文固定六节

开头用两句话交代核心问题与推荐，随后一行元数据：分类、主题、工作状态、成熟度、采用、优先级、评分及成本范围。其余信息合并到以下六节，不逐字段各建一节。

| 二级标题 | 要回答的问题 | 原字段归位 |
| --- | --- | --- |
| 要解决的问题 | 谁在何场景遇到什么障碍，目标、范围及已有确认是什么？ | 背景、问题、目标、范围、当前理解 |
| 当前方案 | 谁执行、输入/输出、状态归谁、正常与失败链如何走？ | 候选方案、推荐、方案推演 |
| 依据与取舍 | 哪条原话/证据支撑什么推论，合理替代、成本与推翻条件是什么？ | 证据、依赖、替代方案 |
| 待确认项 | 少量可直接回答的选择及后果；哪些已经确认、不应重问？ | 开放问题、待决策项、确认范围 |
| 验证与完成条件 | 设计、采用、实验、实施分别完成到哪；缺什么、怎样判定？ | 验证、验收标准、进展 |
| 关联 | 规格、来源、决议、验证和上游问题分别承接什么？ | 关系、DISC/需求/验证ID |

六节用于新Issue的初始快照，不要求每条评论重复六节。复杂方案可在“当前方案”下分三级标题。探索单在同一结构写价值假设、反证/停止条件；实施单写已确认输入、具体交付与验收；条件单写缺口→最小解阻→验证出口；治理单写实际失效→维护机制→迁移→检查。没有待确认项时说明准确范围，不凑审批。

## 发布后只追加：保留每个阶段

用户2026-11-03请求`667d7fc5-0554-4e86-8400-367ff940821c`取代旧的“Issue每轮原位重写”规则。**已发布正文与评论保留原文，包括AI自己的评论；新反馈、纠错、评分/状态变化、推荐替代均以新评论追加。** 不为了同步现状而改旧文字、勾旧清单或改标题，不把旧方案删除后写成从未发生。发布前草稿可以正常修改；本规则不授权关闭、重开、分派或改成员任务。

默认使用评论；如界面确实无法追加评论，只可在旧正文“关联”节末尾追加三级阶段标记的补充，写前核对最新全文，保留原字节且回读前缀。不能以“方便整理”为由使用正文覆写。当前GitHub具备评论能力，本项目正常迭代不使用此后备方式。

当前仓库架构/设计/规范仍原位整合，并由Git保留版本；**Git不会自动保存GitHub Issue正文的完整历史**。阶段形成时保留实际可取得的正文/评论快照、来源定位和哈希；历史缺口明确未知，不从旧设计文档伪造当时Issue内容。当前入口与历史证据分开，见[阶段快照](issue-history/README.md)。

### 选择评论、子Issue或后继Issue

| 情况 | 载体与关系 | 防止的失效 |
| --- | --- | --- |
| 同一目标的新证据、比较、纠错、采用回复、阻挡或收束 | 在原单追加阶段评论，引用前序与准确替代范围 | 不因方案变化抹掉原判断，也不按聊天条数制造Issue |
| 主问题内可独立验收、独立跟进的研究/实施任务 | 确有需要才新建子Issue；父单追加范围/依赖链接，子单初始正文链接父项 | 子任务不重复决定主问题，关系建立不等于指派或批准实施 |
| 原目标发生实质变化，或讨论太长已无法独立评审且有完整新提案 | 新建明确承接的后继Issue，原单追加去向；新单保留来源、已确认范围、未解决项和改变理由 | 不通过改旧标题/正文偷换问题；不自动关闭旧单 |
| 超出用户现有主题、方向不成熟或可能改变产品方向 | 先在原单追加候选与范围变化，交由用户确认再实例化 | 子Issue不是擅自扩展探索分支的许可 |

平台原生父子关系可用且确有必要时使用；否则在父/子两端保留明确链接和“承接＋范围”，标明只是文本关系，不宣称已配置原生子Issue。本轮不为展示图谱批量拆单。

<a id="stage-record"></a>
### 阶段追加记录

同一Issue用稳定编号`I<编号>-P<序号>`标记重要阶段，发布前读最新评论取下一个编号；同一轮可合并相关回复。只有实质新证据、假设变化、候选变化、明确决定、验证结果或阶段收束形成节点；澄清/进度短评可挂到已有阶段，不强行每条消息建节点。

阶段评论按[追加模板](../.agents/skills/discussion-sdd/references/issue-stage-template.md)写：

- **前序与触发**：原评论/用户请求、前序阶段、DISC/需求ID及具体场景；新研究先查同目标的旧尝试。
- **本阶段方案及增量**：旧→新、保持范围、机制/失败例/代价，必须足够独立评审，不能只贴链接。
- **证据与判断**：区分原话、事实、假设、推演、实测和人类采用；链接固定提交/实际run，不用当前分支链接充当历史版本。
- **结果与后续**：采纳/暂缓/否决/结论不足分别写范围、理由与来源；说明停止条件、重启条件及未解决项。阶段总结不是人类批准。
- **项目回写**：本轮怎样保持/改变loom-oi共同承诺，当前规格入口、固定规格版本与验证限制。

“更晚”不自动“更权威”：以明确的人类确认范围和有效证据判断；新提案不能悄悄覆盖旧采用。存在冲突时并列记录并停止依赖该冲突的实施，独立分析可继续。重要决定和关键实验仍用既有ADR/ITER，不再造另一套批准/门槛状态。

<a id="lineage"></a>
### 问题与方案演进记录

本项目用这个描述性名称表示：**围绕一个问题，记录当时的背景与约束、考虑或尝试过的方案、判断依据、阶段结果及后续变化，使人和AI能够还原为什么走到当前方案，并判断旧结论是否仍然适用。** 这不是声称采用了某个已有专业术语或标准。

用户原话“类似于血缘图谱式经验”表达的是可追溯、积累经验和避免无依据重复探索的需求。此前AI直接命名为“经验血缘”不够准确；该类比本身不要求数据血缘系统、知识图谱平台、图数据库或自动推理。阶段表和明确链接即可满足当前需求，必要时再作图。

记录要能回答五件事：当时要解决什么、有哪些条件与候选、依据什么得到判断、后来为什么改变、现在复用或重试需要满足什么条件。来源引用、版本承接、判断修正和证据支持须分别写清；时间先后、父子关系和文字相似都不能自行推出因果。记录中的AI推测、未测方案、人类取舍与实测结果保持原类型；仅因写入KB或被多次引用，不能升级为已验证经验或通用结论。

例如#15：旧进程A/B确认被调整，是因为路径策略会改变负载分析的前提；没有实测就不能写成“拆进程已失败”。可复用的是“先查影响负载的路径条件”这一有适用范围的方法判断，部署方案仍需具体条件与验证。保留当时未知，避免把后来的认识倒写成当时已知。

旧路径`kb/lineage.md`与本节`#lineage`锚点仅保留链接兼容，不定义技术模型。历史原话、已发评论和阶段快照保持原样，通过后续说明纠正含义。

在[kb/lineage](../kb/lineage.md)索引关键阶段和注明类型和理由的关系：来源、沿用、修正/替代、验证/反证、承接。替代只覆盖明确范围，不能解释为方案已采用；时间先后与父子关系都不是因果或批准。展开新方向时先查：原场景/假设→尝试机制→实际结果→为何停止→什么条件变化才值得再试。

重提旧方案须写“与旧尝试相比改变了什么”，例如新需求、拓扑、代码版本、约束或证据；没有变化时复用原结论/未知和剩余条件。重复实验如果是复现/可信度研究，明确这一新目的与判定，不禁止有理由的复验。被否决或暂缓不是永久黑名单，也不因换名称、模型或新对话重新计为全新探索。

已记录的阶段条目/关系和原始快照只追加；发现误记时加更正条目/关系，保留原条目，注明哪项被纠正。索引可维护“当前阅读入口”，但必须从明确关系推导、指向实际节点，不能删除历史或把计划中的回复链接写成已发布。阶段快照是证据，不是第二份实时方案；无需逐条复制闲聊，不新建图数据库、后台定时器或复杂评分。

## 处理评论后的回复与交付

每次处理用户评论，先准备具体方案与受影响仓库产物，再在原Issue追加回应并回读。**阶段评论可同时承担W17的回复职责，无需重复发“已更新正文”。** 链接本轮处理的每条原评论，说明调整/保持/未采纳及理由、实际验证与限制、准确待确认范围；无新选择时写“供核对改动，无新增产品决策请求”。GitHub普通评论不冒充嵌套回复。

发布前重读最新评论并查重，键为“原反馈＋DISC/阶段ID＋本次提交”；并发出现新回复或编号冲突时先重新对照，不能盲发重复节点。读回正文/已有评论的字节与元数据，确认未改旧内容；回读新评论及链接，再追加阶段发布记录。中断时保留已发布评论ID，重试先查是否存在，不复制发送或编辑已发内容。失败如实记录待同步项。

## 分类与状态

| 分类 | 使用范围 | 稳定机器标识（不创建标签） |
| --- | --- | --- |
| 产品 | 场景、体验、价值和范围 | `Product` |
| 架构 | 对象、职责、边界和交互 | `Architecture` |
| 技术 | 协议、状态、算法与性能设计 | `Technical` |
| 探索 | 有价值假设、反证及停止条件的新构想 | `Exploration` |
| 决策 | 充分方案已展开，需要明确人类取舍 | `Decision` |
| 风险 | 已发生缺陷或有触发/后果的潜在失效 | `Risk` |
| 实施 | 依赖已确认、范围已授权的具体执行增量 | `Implementation` |
| 治理 | 工作方法、知识、模板与协作规范 | `Governance` |


选一个主类型；未核验/配置标签时正文元数据生效，不声称标签不存在。本轮不改已有标签或成员字段。

工作状态：待梳理 / 设计中 / 评审中 / 验证中 / 受阻 / 实施中 / 已解决 / 暂缓。方案成熟度：草案 / 方案推演 / 已实验 / 已实现。采用状态：待确认 / 已采用 / 已否决 / 暂缓 / 部分已采用；多范围分别记录。GitHub open/closed单独管理。

采用必须有明确原回复、作者/时间和准确范围；验证只按实际证据。“评审中 / 方案推演 / 待确认”可提交，不代表实施获准；“已采用”也不能替代实验门槛。结构检查通过不证明理解了用户原意。

## 轻量评分


I/U/N/E 使用1–5，C使用1–3；注明日期、评估者和理由，不确定写 待定。本轮均为 AI 初评，非人员安排或最终选择。

| 指标 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- |
| Impact | 局部措辞 | 单个次要场景 | 单模块/主要场景 | 跨模块/多接入 | 核心边界、权限或副作用正确性 |
| Urgency | 以后可选 | 下一阶段 | 当前阶段后段 | 契约/验收前 | 当前核心范围/模型讨论前置 |
| Uncertainty | 已验证 | 少数边界未知 | 机制较明确但待实验 | 关键假设未测 | 多方案与机制均不清楚 |
| Effort | ≤0.5人日 | >0.5–1人日 | >1–3人日 | >3–7人日 | >7人日，需检查边界 |

C=1：主要推测；C=2：有可追溯原文/源码支持，具体方案未实测；C=3：有直接可重复的针对性运行证据。降低 N 不等于提升 C：机制更清楚了，仍可能未验证。

参考分 `S=2I+U+N`（4–20）帮助排列讨论，不自动决定优先级或选型。E/C 单列，不用复杂公式掩盖未知。E 明确估计后续设计验证或实现的哪一部分；本轮各主线的 E 仅指后续设计/实验验证，不含完整产品实现与采购。

P0=有证据的当前严重事故；P1=当前核心边界/正确性/契约前置；P2=有明确价值但可后续收敛；P3=认可但不紧迫。当前没有 P0，不因为存在潜在风险就标紧急。

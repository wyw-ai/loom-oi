# Issue 编写与维护规范

Issue是一个独立问题的当前评审入口。先读原件、最新正文/评论及关联规格，完成求解，再写正文；主类型、状态、评分帮助定位，不代替方案。文档职责见[结构规范](structure.md)，规格确认及实施门槛见[SDD](sdd/README.md)。

## 一单一个确认目标

先说明问题属于loom-oi的哪项用户结果/共同契约，再判断能否独立确认。会改变同一结果或成本前提的研究方向应作为同一主问题的方案维度；拆单依据共同验收和真实依赖，不能按组件名切断因果。按[项目收束规则](sdd/README.md#project-convergence)回写整体影响。

标题写用户能力或具体取舍，保留`[alpha][分类]`，不放修订号。多个问题只有共享同一决定且不能分别收敛时才合并；关系用“类型＋目标＋理由”。同一目标更新现有单，不按每条聊天/每个测例建单。新探索主题由用户创建。治理本身是当前诉求时可独立建治理单，不能用治理单代替产品方案。

## 中文显示与稳定标识

依据[#14回复](https://github.com/wyw-ai/loom-oi/issues/14#issuecomment-6596717601)，当前Issue标题、元数据、状态、分类和关系统一中文，八类沿用现有含义，先不增子类。当前活动单均无GitHub标签，暂以正文分类作为权威，避免同时维护一套重复标签；以后确需平台筛选再统一迁移。

[词汇映射](vocabulary.json)供检查器与生成目录使用；JSON内部枚举、工具参数、历史原始证据和已有采用凭据保留稳定机器值。协议的Ready/NotReady/Unknown属于线上的具体语义，不能因治理中文化改协议。新正文解释为就绪/未就绪/未知，并在需要时保留代码名。

元数据采用“分类、主题、工作状态、成熟度、采用、优先级、评分”。混合范围用“部分已采用”，准确范围写在正文；验证状态单列。中文显示不改变open/closed、不扩展批准，也不把“已通过物料检查”写成“已通过实验”。

## 正文固定六节

开头用两句话交代核心问题与推荐，随后一行元数据：分类、主题、工作状态、成熟度、采用、优先级、评分及成本范围。其余信息合并到以下六节，不逐字段各建一节。

| 二级标题 | 要回答的问题 | 原字段归位 |
| --- | --- | --- |
| 要解决的问题 | 谁在何场景遇到什么障碍，目标、范围及已有确认是什么？ | 背景、问题、目标、范围、当前理解 |
| 当前方案 | 谁执行、输入/输出、状态归谁、正常与失败链如何走？ | 候选方案、推荐、方案推演 |
| 依据与取舍 | 哪条原话/证据支撑什么推论，合理替代、成本与推翻条件是什么？ | 证据、依赖、替代方案 |
| 待确认项 | 少量可直接回答的选择及后果；哪些已经确认、不应重问？ | 开放问题、待决策项、确认范围 |
| 验证与完成条件 | 设计、采用、实验、实施分别完成到哪；缺什么、怎样判定？ | 验证、验收标准、进展 |
| 关联 | 规格、来源、决议、验证和上游问题分别承接什么？ | 关系、DISC/需求/验证ID |

复杂方案可在“当前方案”下分三级标题。探索单在同一结构写价值假设、反证/停止条件；实施单写已确认输入、具体交付与验收；条件单写缺口→最小解阻→验证出口；治理单写实际失效→维护机制→迁移→检查。没有待确认项时说明准确范围，不凑审批。

## 原位更新与历史保真

每轮读取评论后将有效反馈合入上述六节，移除已被替代的推荐，不追加整块“本轮反馈”。保留原评论；历史方案用对应DISC基线/Git快照追溯，当前正文只留必要来源和明确决议。正文必须自足：不打开链接也能判断方案、一个失败例和主要取舍；细节可回链，不能成为链接目录或再次复制完整设计。

每轮讨论融合实际更新相关Issue供开发者确认；只有新独立目标才建单。不得擅自关闭、重开、指派、修改成员任务、合并或部署。已接受一个范围不等于整单完成；历史评论与当前正文冲突时回到明确原回复，并同步受影响规格/图/指纹。

## 处理评论后的回复

每次处理用户的Issue评论，完成正文及受影响仓库产物的同步后，必须在原Issue评论区回应，让用户直接核对本轮改动。正文维护当前方案，评论保存“这次如何处理了你的反馈”，两者都要完成；聊天中的交付总结不能代替Issue回复。

回复包含以下内容，按实际复杂度简写，不复制整篇正文：

1. **对应原评论**：链接本轮处理的用户评论；一条有多项诉求时逐项回应，同一Issue多条评论可合并回复但要分别映射。GitHub普通Issue用新评论加原评论链接，不冒充嵌套回复。
2. **具体改动**：说明原状态→当前状态、采纳/调整/未采纳及理由，并链接相关提交、文档或关联Issue。不能只写“已处理”“见正文”。
3. **验证与限制**：列实际检查及未做事项；实验准备、实际运行和阶段通过分别说清。无变化也解释保持理由，受阻则说明已完成部分、缺口与下一步。
4. **确认范围**：指出仍需用户判断的新取舍；已明确采用的内容只回报落实，不重复要求批准，不把回复发出视为用户再次确认。无新决策时明确“供核对改动，无新增决策请求”。

发布前重新读取最新评论，检查同一原评论和同一轮改动是否已有回应，避免重试或接续任务重复发送。正文/仓库回读后发布，随后实际回读评论正文与链接；如果同步或回复失败，报告具体待完成项，不宣称闭环完成。原评论保留，不自动@其他成员或改变负责人/开关状态。

## 分类与状态

| 分类 | 使用范围 | 稳定机器标识（不创建标签） |
| --- | --- | --- |
| 产品 | 场景、体验、价值和范围 | `Product` |
| 架构 | 对象、职责、边界和交互 | `Architecture` |
| 技术 | 协议、状态、算法与性能设计 | `Technical` |
| 探索 | 有价值假设、反证及停止条件的新构想 | `Exploration` |
| 决策 | 充分方案已展开，需要明确人类取舍 | `Decision` |
| 风险 | 已发生缺陷或有触发/后果的潜在失效 | `Risk` |
| 实施 | 依赖已确认、范围已授权的具体执行增量 | `Implementation` |
| 治理 | 工作方法、知识、模板与协作规范 | `Governance` |


选一个主类型；未核验/配置标签时正文元数据生效，不声称标签不存在。本轮不改已有标签或成员字段。

工作状态：待梳理 / 设计中 / 评审中 / 验证中 / 受阻 / 实施中 / 已解决 / 暂缓。方案成熟度：草案 / 方案推演 / 已实验 / 已实现。采用状态：待确认 / 已采用 / 已否决 / 暂缓 / 部分已采用；多范围分别记录。GitHub open/closed单独管理。

采用必须有明确原回复、作者/时间和准确范围；验证只按实际证据。“评审中 / 方案推演 / 待确认”可提交，不代表实施获准；“已采用”也不能替代实验门槛。结构检查通过不证明理解了用户原意。

## 轻量评分


I/U/N/E 使用1–5，C使用1–3；注明日期、评估者和理由，不确定写 待定。本轮均为 AI 初评，非人员安排或最终选择。

| 指标 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- |
| Impact | 局部措辞 | 单个次要场景 | 单模块/主要场景 | 跨模块/多接入 | 核心边界、权限或副作用正确性 |
| Urgency | 以后可选 | 下一阶段 | 当前阶段后段 | 契约/验收前 | 当前核心范围/模型讨论前置 |
| Uncertainty | 已验证 | 少数边界未知 | 机制较明确但待实验 | 关键假设未测 | 多方案与机制均不清楚 |
| Effort | ≤0.5人日 | >0.5–1人日 | >1–3人日 | >3–7人日 | >7人日，需检查边界 |

C=1：主要推测；C=2：有可追溯原文/源码支持，具体方案未实测；C=3：有直接可重复的针对性运行证据。降低 N 不等于提升 C：机制更清楚了，仍可能未验证。

参考分 `S=2I+U+N`（4–20）帮助排列讨论，不自动决定优先级或选型。E/C 单列，不用复杂公式掩盖未知。E 明确估计后续设计验证或实现的哪一部分；本轮各主线的 E 仅指后续设计/实验验证，不含完整产品实现与采购。

P0=有证据的当前严重事故；P1=当前核心边界/正确性/契约前置；P2=有明确价值但可后续收敛；P3=认可但不紧迫。当前没有 P0，不因为存在潜在风险就标紧急。

# Issue 管理规范

状态：alpha 工作规范 v0.1；依据用户 2026-11-02 的 Issue Engineering 指令建立。规范可以使用，不构成产品架构决议，也不授权合并主干。

## 1. 管理入口与边界

GitHub Issues 是已实例化问题的当前状态来源；[alpha 问题索引](alpha-issues.md)保存编号映射、来源及尚未获准创建的方向候选。[讨论蒸馏](alpha-discussion.md)保存团队表达，[架构稿](distributed-architecture-conclusions.md)保存设计内容。不要将同一份 Issue 正文复制到多个文档持续维护。

- 创建前查阅 open/closed Issues、相关评论、标签、模板及当前规范；以问题边界、目标和来源去重，不只匹配标题。
- 来源与价值明确的设计缺口、研究问题和已授权工程任务可以创建。方向有歧义、构想未成熟或可能改变产品范围时，先放候选区，用户确认后才创建。
- 新建 Issue 默认 `Triage`，不是承诺排期；不分配负责人、不设截止时间、不自动修改成员任务。
- AI 可以整理证据、补反例、提出方案和更新进展；用户掌握方向选择、接受风险、关闭问题及合并权限。没有额外授权，不关闭/重开已有 Issue、不写 Accepted 决议。
- Issue 属于仓库级资源，没有 Git 分支隔离；必须写明 `Topic: alpha`。本轮代码和文档仅更新已有 `alpha`，不创建其他探索分支。

## 2. 分类

每个问题选一个主要 Type；必要时在正文描述次要维度，避免为同一问题创建多个分类副本。

| Type | 使用时机 | 标签映射 |
| --- | --- | --- |
| Product | 用户场景、接入体验、产品收益与范围 | `type:product` |
| Architecture | 对象、模块、职责与系统边界 | `type:architecture` |
| Technical | 协议、状态、性能、可行性与技术验证 | `type:technical` |
| Exploration | 尚需验证的价值假设和新构想 | `type:exploration` |
| Decision | 需要人类选择的方案及其权衡；建单前仍须满足候选确认规则 | `type:decision` |
| Risk | 缺陷、潜在失效及明确设计缺口 | `type:risk` |
| Implementation | 已授权、依赖明确、可验收的执行任务 | `type:implementation` |
| Governance | 模板、追踪、证据、规范及决策机制 | `type:governance` |

辅助映射仅保留 `topic:alpha`、`priority:p0`–`priority:p3`、`status:<状态小写>`，不为每个分数建标签。不删除或覆盖项目已有标签。

**本次接入限制（2026-11-02）：** GitHub 连接器可以创建和更新 Issue，但不能列出/创建仓库标签；labels 查询被该接口拒绝。浏览器未登录私有仓库，无法补查。因此不能断言仓库“没有标签”，本轮没有创建、覆盖或应用未经核实的标签。Type/Topic/Priority/Status 暂以 Issue 正文表格为准；上表是映射规范，非已部署标签。具备管理入口后先查现有名称并复用，再补齐映射。

## 3. 最小问题上下文

使用 [通用模板](../.github/ISSUE_TEMPLATE/problem.md) 或 [探索/决策模板](../.github/ISSUE_TEMPLATE/exploration-decision.md)。字段按类型裁剪，不用空话填满。

必需：Title、Type、Topic、Context/来源、Problem、Goal、Scope、Current Understanding、Open Questions、候选方案、Acceptance Criteria、Priority、五个评价指标、Status、Relations。

- 来源尽量固定到提交与章节；原始聊天仅保存必要摘要和已有证据索引，不上传无关内部内容。注明是否实际重新核对原件。
- 当前认识区分【团队共同方向】【用户已确认决议】【AI 建议】【未验证假设】。聊天中的赞同不自动等于对完整方案的批准。
- 探索增加价值假设、反证条件、验证方法、预期输出与停止条件；决策增加选项成本和对其他问题的影响。
- 工程任务写清前置已确认决策、具体行为与验证方式；风险注明触发条件、后果及已有保障，未观察到事故就不能称线上缺陷。
- 验收可以是设计、比较报告或测量计划。计划交付不等于实验通过，实验通过不等于用户批准设计。

## 4. 量化方式

Impact、Urgency、Uncertainty、Effort 使用 1–5；Confidence 使用 1–3。每次评分注明评估时间、依据和评估者。当前 Issue 的初评均为 AI 建议，允许用户调整。

| 指标 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- |
| Impact 影响 | 局部措辞/体验 | 单一非关键场景 | 单模块或主要场景 | 跨模块/多种接入 | 核心边界、权限或副作用正确性 |
| Urgency 紧迫 | 后续可选 | 下一阶段前考虑 | 当前阶段后段需要 | 接口/验收冻结前必需 | 阻塞当前核心范围或模型讨论 |
| Uncertainty 不确定性 | 已验证，执行为主 | 少量边界未知 | 有候选，证据不完整 | 关键假设未验证 | 多方案未测，差异未知 |
| Effort 成本 | ≤0.5 人日 | >0.5–1 人日 | >1–3 人日 | >3–7 人日 | >7 人日，需再拆界 |

Effort 估算的是 **本 Issue 的交付物**，不默认包含未来生产实现、采购或长期运维；不是人员承诺。Unknown 可写 `TBD` 并注明补估条件，不造精确数字。

Confidence：1=主要依赖推演或未核实说法；2=有可追溯文档/源码证据但未完成针对性验证；3=有直接、可重复的实验或实现证据。它评价问题与评分的证据基础，不代表方案正确概率。

调查顺序参考分：`S = 2 × Impact + Urgency + Uncertainty`，范围 4–20。更大的影响和未知优先进入讨论；Effort 与 Confidence 并列展示，不塞入复杂乘除公式。未知分项时不计算总分。同分先看依赖，再看成本。分数不能自动决定 Priority、选型、排期或是否创建 Issue。

| Priority | 含义 |
| --- | --- |
| P0 | 有证据的当前严重事故/紧急阻断，需要即时处理；不用于所有潜在风险 |
| P1 | 当前架构范围、契约或关键正确性的前置问题 |
| P2 | 当前主题有明确价值，但可在边界清楚后推进的证据工作 |
| P3 | 低紧迫度的已认可后续问题，不默认排入本轮 |

## 5. 生命周期与关联

| Status | 含义及转入条件 |
| --- | --- |
| Candidate | 文档中的待确认候选，尚未实例化为 GitHub Issue |
| Triage | 已建单，检查范围、依赖与验收；不等于已排期 |
| Ready | 问题可独立推进，前置与权限明确 |
| In progress | 已实际开展研究或实施，有进展证据 |
| Blocked | 被具体 Issue、未决条件或环境阻塞；必须写解除条件 |
| Awaiting decision | 证据/选项已准备，等待用户方向判断 |
| Review | 验收材料可评审，待核对结果及关联文档 |
| Resolved | 用户确认解决并授权关闭后的状态 |
| Deferred | 用户决定暂缓；保留重启条件，不自动关闭 |

通常按 Triage → Ready → In progress → Review 推进；可以进入 Blocked/Awaiting decision 后返回。候选获准创建时转 Triage，选项获准时仍要检查验证和文档是否完成。GitHub open/closed 与上述工作状态分开：Review、Awaiting decision、Deferred 均可保持 open。

关系使用三种普通链接：`Tracks`（父项跟踪）、`Depends on`（强前置）、`Related to / Informs`（相关或提供证据）。不要把提供证据的任务与待决策项画成相互等待的死循环：研究可以比较所有候选，只有契约冻结/实现依赖最终选择。

本轮使用父项 Markdown 清单和正文回链，未设置 GitHub 原生 Sub-issues/Projects 工作流；不得把普通链接描述为已创建原生父子关系。D1–D6 是候选编号，ALPHA-01–08 是稳定整理编号，真正的 GitHub 编号以索引为准。

## 6. 与 AI 持续协作

指定 Issue 后，先读正文、全部相关评论、关联问题、来源快照及当前架构；先确认哪些结论已改变，再开始研究。保留用户决策原文或可追溯引用与日期，不覆盖别人的讨论。

更新时：整理新增证据与反例 → 修订当前认识/方案/验收 → 记录变更原因和状态 → 检查受影响的 Issue、D 项、图和契约示例。设计未被接受只更新候选；用户明确确认后才改成正式决议。合并和关闭分别取得授权，不能因为勾完清单自动执行。

每次主题评审/阶段收尾时检查重复、互相冲突、阻塞依赖、无决策人结论及来源失效；超过 14 天无进展可标记供人工查看，不能自动判断废弃、关闭或转派。本轮未设置定时任务。

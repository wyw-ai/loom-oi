# 问题与方案演进：防止重复探索与图谱方案

状态：轻量实现已按W23/W24授权进入[TASK-002](../../spec/TASK-002-issue-evolution/README.md)，在单任务feature交付，合入alpha前以该分支为准。由[DISC-005 r4](../changes/DISC-005.md#lightweight-implementation)和#14承接。实现为Git阶段JSON＋一个Python标准库只读脚本，每次直接扫描；无数据库、持久索引或后台服务。本文描述协作能力，不增加loom-oi运行时模块。使用入口见[kb/evolution](../../kb/evolution/README.md)，调研取舍与验证见[任务目录](../../spec/TASK-002-issue-evolution/README.md)。

## 1. 目标与现状

目标是让后续讨论能利用过去的判断：发现实质相同的尝试，解释为什么当时停止；条件改变时允许重试；新证据出现时检查哪些旧建议需要重评；把实际遗漏反向改进工作方法。**保存历史只是输入，真正要形成的是检索、比较、判断、验证与回写的循环。** 不能保证永不犯错，也不能用历史阻止合理探索。

截至本轮基线`d53ad85c98805b02e1ce2192d0e6a3a2ff022de3`：

| 能力 | 已有内容 | 尚缺的能力或证据 |
| --- | --- | --- |
| 保留探索阶段 | Issue只追加、真实原文快照、固定提交 | 历史不完整；当前重点记录#14/#15，未覆盖所有问题 |
| 再次尝试前比较 | 查原假设、停止理由、重启条件，允许有目的复验 | 主要靠AI阅读；没有相似机制检索、条件匹配工具或漏检统计 |
| 关联阶段与依据 | kb/lineage已有节点、带理由的关系表 | 是人工关系索引，尚无机器可查询的完整依赖模型或自动影响分析 |
| 改进工作方法 | kb/lessons、prompt/内容评审按真实失效修改 | 尚无持续可比较的漏判、误拦和维护成本数据；格式检查不证明防重复有效 |

上轮“阶段表和明确链接即可满足当前需求”证据不足，“不新建图数据库”的绝对措辞也提前排除了候选。准确结论是：用户没有指定实现技术，AI应展开比较；既不因类比强行选图技术，也不因此排除它。此处补充能力方案，旧发布内容按原样留存。

## 2. 先把防重复过程做完整

触发点是提出新建议、准备重做实验、收到反证/确认或准备收束方案；由正在执行本轮任务的AI完成，不暗示已有后台监听。

| 步骤 | 输入与操作 | 必须输出什么 |
| --- | --- | --- |
| 找历史 | 按项目目标、核心机制、约束和失败方式检索；先沿已有引用，再查全库和可访问Issue；标题相似仅辅助 | 查过哪些范围、找到哪些相关尝试、哪些来源不可访问；“未找到”不等于从未讨论 |
| 比条件 | 将当前与旧尝试的目标、机制、权限/故障边界、环境/版本、预算及证据并排比较；只比较与判断有关的条件 | 相同点、变化点、未知项与原文定位；哈希不同不等于机制不同，名称相同也不等于条件相同 |
| 作判断 | 按下表选择复用、继续验证、重新评估或暂缓；相似检索不能自行拒绝方案 | 判断及理由，保留人类采用/否决的准确范围；冲突不能由“最新AI回复”裁决 |
| 限定验证 | 新问题给最小对照、能区分候选的观察和结束条件；无可辨别的新问题时先补条件 | 这轮能学到什么、什么结果会改变建议；预算由实际任务约定，不设全项目任意次数禁令 |
| 回写影响 | 追加尝试及结果，沿明确的依赖/替代关系检查受影响建议与文档；复用成功案例也要沉淀 | 旧记录不改；影响清单和保持/修订理由；实验则执行既有ITER闭环，正常讨论不制造实验记录 |
| 修正方法 | 记录漏掉旧尝试、误拦新方案、错误归因或过期引用的具体发生过程 | 修改对应检索词、关系、适用条件或工作规则；用反例复查，避免只增加口号 |

判断不能简化为“以前失败过就拒绝”：

| 对照结果 | 建议处理 |
| --- | --- |
| 核心机制、关键条件均未变，旧结论证据仍适用 | 引用旧结论与缺口，说明复用；不把改名包装成新探索 |
| 旧记录只是未测、缺材料或当时优先级低 | 保留未知；解决材料/优先级条件后可以继续，不标为技术失败 |
| 关键条件改变或出现新证据 | 形成新尝试版本，解释旧结论为何不能直接套用，验证改变部分 |
| 明确要检验旧证据的可靠性 | 作为复现实验，记录新的检验目的和独立性；不以“重复”禁止 |
| 关键条件未知、旧来源缺失或互相冲突 | 保留待核对；可继续独立分析，不能据此声称旧路已证伪或新路已获准 |

跨Issue传播的是“需要复核”的线索：若某证据被纠正，找出依赖它的判断，再核实每条依赖是否必要、是否有其他支撑。不能沿任何“相关”链接机械宣布所有下游失效，更不能自动撤销人类决定、改Issue状态或关闭问题。

## 3. 图谱要分清三个层次

| 层次 | 对本需求的具体作用 | 仍不能解决什么 |
| --- | --- | --- |
| 关系模型 | 明确问题、方案版本、条件、证据、判断/决定以及修正、依赖、支持/反驳关系；便于跨Issue追踪 | 关系是否真实仍须原文与分析；连线不证明因果 |
| 图形视图 | 按一个问题展示来路，或按一项条件展示受影响判断；可以从同一记录生成 | 全库大图容易遮蔽细节；漂亮图形不能代替条件比较 |
| 图查询与存储 | 支持机器沿关系找来源、替代版本和受影响判断；可由文件读取后遍历，也可由专门数据库提供 | 数据库不会自行识别同义机制、验证证据或代人决策 |

**明确关系模型、按需关系视图与数据库是不同选择。** W23/W24授权的本次实现只采用前两项和文件内存遍历；数据库不在任务范围。此前r3仅为建议的状态仍保留在历史记录，不倒写为当时已批准。

借鉴边界：W3C [PROV-DM（2013推荐版）](https://www.w3.org/TR/2013/REC-prov-dm-20130430/)定义实体、活动、责任主体及派生等溯源关系，可以启发来源和生成过程的表达。Michael Nygard的[ADR原文](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)强调决定的背景、状态、后果和替代记录。二者提供局部参考；本文的“防重复循环、条件比较和图存储取舍”是针对本项目的设计推论，不宣称这些资料已经验证了本方案，也不强制采用完整PROV/RDF规范。

## 4. 三种可执行候选

| 候选 | 机制与部署 | 适用情况 | 代价与局限 |
| --- | --- | --- | --- |
| A：现有Markdown＋人工执行循环 | 阶段评论、关系表和条件对照继续由人/AI维护；用文件搜索和源链接查阅 | 问题少、关系简单；可作为当前对照 | 最少新工具，但跨单关系容易漏读，重复文字和索引漂移依赖人工发现 |
| B：Git内结构化关系记录＋按需查询/视图 | 重要记录和关系按稳定ID追加；每次从文件读取，按问题查来路、相似尝试候选及影响，生成图源码 | 需要跨Issue复用和影响检查，又希望继续在仓库审阅、无常驻服务 | 要定义记录格式与迁移；语义匹配仍需AI/人工核对；维护和查询收益需实测 |
| C：专用图存储/查询服务 | 在B的模型和来源基础上提供持续查询、增量接入与多用户访问；需明确写入权威和同步 | B在真实数据上不能满足已明确的查询时延、并发或在线协作需求时 | 增加部署、权限、备份、同步冲突和迁移责任；不能仅凭Issue变多就宣称必要 |

**本次落实B的最小版本，A仍可直接使用，C仅保留原讨论中的条件候选。** 若B维护成本高、识别效果未改善，可以缩回A；若文件扫描满足实际查询预算，继续使用。当前没有数据支持专用数据库或具体性能阈值，不能因预期增长主动增加服务。

## 5. B怎样实际工作

沿用已有Issue、DISC、claim、run和阶段ID，不给每条闲聊造节点。仅在需要独立引用、复用或影响分析时，把条件、方案版本或判断单列为记录。方案记录应解释“谁对什么做什么、依赖何种条件、预期结果与失败方式”，不只存名称。

最小记录包含稳定ID、类型、所属问题/阶段、范围与正文摘要、来源URL及固定版本/实际快照、来源作者和时间、记录者与记录时间。条件、证据级别、采用状态分别表达；未知值保留未知。关系至少包含起点、终点、类型、适用范围、理由与来源。抽取是AI建议时标为待核对，不能把AI身份写成原话作者。

关系先用来源、承接、依赖、支持/反驳、修正/替代；“相似”只作检索候选，不能代替它们。阶段的先后、证据的反驳与方案的人类否决是三件事。仅时间/替代版本等有序关系检查循环，讨论反复、相互反驳和跨单相关可以成环，不将全图错误限制为树或单一有向无环图。

以按阶段分文件的追加记录为查询来源；更正新增记录并指明准确替代范围。当前脚本不维护持久索引，不自动生成权威的“最终已采用方案”；输出输入指纹、来源哈希和覆盖缺口，存在替代或分歧时提示核对准确范围，不用时间戳自动选赢家。来源作者和原时间保留在快照，整理者和整理日期记录在阶段文件，不能混为一谈。

查询应返回“匹配原因＋旧条件/结果＋来源＋当前差异＋覆盖缺口”，而非一个重复分数。第一版可以字段/词项查找加关系遍历；只有测出漏检才评估语义检索。无论采用哪种检索，最后都要核对原文，避免两个同名“缓存”被误判为同一机制。

同源讨论的多次上传、转述和AI摘要归到同一来源组；不能因为五篇摘要都引用一次实验就算五份独立证据。GitHub旧评论与快照继续只追加；同步失败保留待同步，恢复前按来源/事件ID去重。只处理任务授权且可读取的材料，敏感原始讨论继续按既有脱敏范围保存。

四类核心查询为：这个建议为什么出现；这个机制以前在何种条件下尝试过；某条件/证据改变会影响哪些判断；有哪些判断仍冲突或缺依据。没有来源定位的结果不能作为拒绝新探索或批准实施的依据。

| 场景 | 应得出的结果 | 能发现的失效 |

| #15把原A/B问题改名为“独立转发工作器”，但路径/负载/故障条件仍未明确 | 命中I15-P01及EXP-CH-01；复用“先检查路径对负载的影响”，仍不能先冻结进程 | 仅按标题查重会漏；图里只有Issue节点也无法看出机制相同 |
| 后来路径和代表负载已固定，新增硬要求“中继退出后控制仍存活” | 形成条件变化的新比较；可研究进程/主机隔离，不能沿旧经验永久禁止B/C | 硬拦截“过去讨论过”会误伤合理重试；要求真实约束来源，不把本例当已新增产品需求 |
| 未来某项容量数据被纠正 | 沿数据→容量判断→部署建议找出需重评项；检查其他依据后再决定修订；R人类采用不自动撤销 | 将所有相关边当依赖，或把证据纠错等同撤销全部决策 |
| 本轮用户要求展开图谱取舍 | 识别r2“未指定技术→表格足够/排除数据库”的推论缺口，保留语义澄清但重新比较实现 | 经验记录只做防旧路，反而把早先AI建议冻结成不可挑战的规则 |

这是基于现有记录的纸面推演，后两类含明确的未来/假设输入；无新增产品实测。历史样例必须保留当时可见材料，不能把之后的答案泄漏给测试执行者。

## 7. 如何验证和值得迭代什么

先用#14/#15可核实阶段做一小批同条件改名、条件已变、来源缺失、证据被更正和相互冲突的任务；由人工固定相关记录与判定理由，再分别用A/B完成。冻结输入版本，比较同一批任务，并用新改写的留出案例核对。已见过的样例只作回归，不能宣称独立泛化。

记录三类实际数量和案例：漏掉应复用的旧尝试；误拦有理由的新尝试；不能追溯到原文或错用适用范围的判断。另记录新增维护时间、查询时间及同步错误。小样本同时报分子/分母和具体错例，不编造成功率。语义结论由人核对，工具只检查ID/引用/版本等可确定部分。

若只是把旧内容搬成JSON而没有减少上述失误，就没有证明B值得推广。依据具体失误修订关系粒度、检索策略和适用条件，再复查是否引入新的误拦。检查器通过不能替代这些行为证据。

## 8. 当前交付与尚未证明的部分

TASK-002提供validate/search/compare/trace/impact/graph，完整字段和规则只在[使用说明](../../kb/evolution/README.md)维护。六个有来源的初始节点用于检验真实案例；自动化反例验证条件变化、未知、证据冲突和有依据复验的分支。历史保真必须指定可信Git基线，首次导入前的基线检查0份记录不能冒充未来保护。

[验证记录](../../spec/TASK-002-issue-evolution/verification.md)区分单元测试、实际命令回放与独立只读任务；它们证明有限输入的行为，没有证明团队重复探索减少比例、普遍语义召回率或大规模性能。前节A/B真实团队效果比较仍是后续依据实际漏判触发的验证方向，不冒充本轮已完成。未登记同义词、遗漏条件和错误关系仍可能误导，因此保留原文核对与人工决定；无数据库、完整历史迁移或产品实验承诺。

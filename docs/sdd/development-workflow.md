# SDD 开发流程规范

2026-11-03。依据用户请求 `6eb9ade9-3e40-48d7-b9b1-c45f5de40245`：按文档规范维护各类文档，本次任务落在 `spec/`；方案完全确认后创建并推送单任务 `feature/` 分支；单测覆盖率至少 95%；提交 MR 前核对文档与代码一致性。四项约束自本轮起适用。

本页定义开发交付规则；[SDD 总入口](README.md)保留讨论与确认链，[结构规范](../structure.md)定义长期文档职责，执行步骤在 [SDD Development](../../.agents/skills/sdd-development/SKILL.md)。GitHub 的 PR 与本文 MR 含义相同。

## 1. 文档先行，一个任务一个目录

每项任务分配稳定 ID，使用 `spec/<任务ID>-<简述>/README.md`，从[任务模板](../../spec/_template/README.md)创建。小任务在一份文件里维护全部内容；复杂任务可在同一目录拆分方案、计划、验证记录，README 保持唯一入口。

任务必须有一个可独立验收的目标，明确范围与非目标、需求和验收条件、方案与影响、实施步骤、确认记录、验证证据、MR 前一致性记录。实现、测试、迁移、必要文档同步是该目标的子步骤；可独立验收的第二个目标必须另建任务。

| 文档 | 维护内容 | 与本次任务的关系 |
| --- | --- | --- |
| `docs/concept`、`docs/architecture`、`docs/modules` | 产品定位、共同契约、模块规格 | 按影响原位更新；`spec/` 引用，不复制完整说明书 |
| `docs/designs`、接口/配置/使用文档 | 当前方案和可用行为 | 设计阶段标明待实现，交付前与实现核对 |
| `docs/changes/DISC-*`、Issue | 讨论来源、需求和确认范围 | 一个讨论可拆成多个任务；每个任务精确引用本次采用范围 |
| `spec/<任务ID>-<简述>/` | 本次任务的方案、确认、计划、测试和交付记录 | 一个任务一个目录、一个开发分支、一个 MR |
| `kb/`、ADR | 来源和决定索引、重要决策 | 引用原始确认；不另维护一套当前方案 |

`spec/` 历史任务保留其当时范围与验证证据，不能充当长期现行契约；后续任务不改写旧任务的结论冒充当时已验证。修改同一任务草案时原位整合，旧版本交给 Git。新增长期文档继续登记 `docs/catalog.json`；任务目录由 `spec/README.md` 导航。

## 2. 完整确认后再创建开发分支

顺序必须为：编写任务文档及受影响规格草案 → 沟通消除本任务阻塞项 → 确认整个任务方案 → 创建 `feature/` 分支并先推送文档 → 实现与单测 → 文档一致性检查 → 提交 MR。

“完全确认”指本任务的目标、边界、对外行为、方案、验收条件和适用依赖均已明确；不要求整个项目的其他问题全部解决。记录确认人的原始指令/评论、可定位时间或请求 ID、确切文档版本/指纹和确认范围。明确且完整的用户任务指令本身可以构成确认，无需机械重复询问；AI 不得替人确认未明确的产品取舍。

- 待确认时可以准备文档、调查和验证方案，不提前创建该任务的 `feature/` 分支、不开始产品实现。需要外部评审时使用已有讨论入口。
- 部分确认不等于整个任务确认。可把完整确认、独立可验收的部分拆为新任务，记录依赖；不能借拆分绕过未决条件。
- 确认后接口、权限、失败语义、验收范围发生实质变化，暂停受影响实现，更新方案并取得对应确认。拼写、导航修复不扩大范围，不要求重复确认。
- 产品实施仍需通过原有确认链和适用实验门槛；采用开发流程不代表任何产品方案获准。

## 3. 每个开发分支只包含一个任务

分支命名为 `feature/<任务ID>-<简述>`。从已确认的目标分支最新提交创建，记录目标分支与基线 SHA；禁止自行猜定为 `main`。分支绑定的任务 ID 创建后保持不变。

1. 创建前核对工作区，没有其他任务的未提交改动；有则隔离，禁止丢弃或一起带入。
2. 第一次提交只包含本任务的 `spec/` 文档、必要的长期规格更新与导航。先推送并核验远端文档，再开始产品代码实现；文档尚未成功推送时不能宣称已进入开发阶段。
3. 分支内所有后续提交、文件差异、测试、文档和 MR 均归属同一任务。不得用同一任务名包裹两个独立目标，不复用已合并分支开展下一任务。
4. 发现新需求或顺手修复项，记录为另一个任务，另行确认和开分支；必要前置任务写依赖关系，不混入当前分支。
5. 与目标分支同步只吸收其已有变更，不引入别的尚未合并 feature；任务边界按相对目标分支的 MR 差异核对，不把已有基线历史计为本任务改动。

本规则约束承载开发任务的工作分支。`main`/`alpha` 等集成或讨论分支可以汇集已合并历史，但不得继续直接承载新的混合开发任务；既有历史不重写。本次规范建设是一个已由用户明确提出的独立文档任务，也用独立 feature 保存。

## 4. 单元测试覆盖率至少 95%

对包含可执行代码变更的任务，单元测试必须全部通过，**项目受管自有源码总体以及本次变更涉及的各模块，其行覆盖率（或语言工具等价的语句覆盖率）分别达到 95% 或以上**。只测试改动文件、用一个高覆盖模块平均抵消另一个低覆盖模块，均不满足要求。

- 统计口径、源码根目录、模块边界、测试命令、覆盖率工具和排除项在任务方案中预先写清；优先使用项目已有工具。包含未执行到的源码，分母不得只统计已加载文件。
- 只使用单元测试生成的覆盖率报告，不用集成/E2E/手工运行的混合报告代替。至少测试正常、边界、错误、权限与状态分支等本次适用行为，不能以无有效断言的调用堆覆盖率。
- 第三方依赖、工具生成代码及测试代码按明确口径排除；不得为达标临时排除难测业务源码、加忽略标记或降低阈值。没有测试框架就先补齐测试能力。
- 报告保留测试命令、工具版本、源码提交 SHA、运行环境、覆盖分子/分母、总体与模块百分比和可读取的报告/CI 链接。缺报告、旧报告、测试失败、覆盖率不足或工具不可用均为阻塞；不能把未运行写成通过。
- 支持分支覆盖率的工具同时报告该指标，用于发现遗漏；不能把行/语句和分支覆盖率混为一个数。
- 仅文档/技能文字变更，且无可执行代码、构建、运行配置或生成行为变化时，记录“单测覆盖率不适用”及 diff 范围证明，执行文档与技能检查；不得写“100%”或伪造报告。只要含代码变化，不能用“文档任务”标签免检。

覆盖率是最低门槛，不能替代关键行为断言、回归验证、实验门槛或安全边界核对。当前仓库尚无 OIS/OIC 产品实现；本规则不声称已经配置了自动覆盖率拦截。首个代码任务须配置相应测试/CI 门禁，未具备前用可复现的本地检查执行同一门槛，不能降低标准。

## 5. MR 提交前必须检查文档与代码一致性

检查覆盖本任务最终 diff 与受影响的长期文档，不能只检查 `spec/`。在任务记录中逐项填写：**文档章节 → 对应实现符号/文件 → 测试或实际核验 → 结论 → 修正**。无影响项写具体理由，不允许只勾“文档已更新”。

| 必查项 | 核对内容 |
| --- | --- |
| 需求和验收 | 每条需求都有实现与验证；未实现内容明确标记，不写为已支持 |
| API、CLI、配置 | 名称、类型、必填项、默认值、返回值、错误码与实际实现一致 |
| 行为和边界 | 权限、状态迁移、超时、重试、取消、失败与恢复语义一致 |
| 数据和兼容性 | Schema、迁移、持久化、升级和回滚说明与代码一致 |
| 使用、部署和示例 | 命令、示例、依赖版本、环境变量可按文档复现；示意伪代码明确标记 |
| 架构和导航 | 组件职责、连线/流程图、模块关系、链接及入口与改动一致 |
| 测试和状态 | 测试实际覆盖承诺；覆盖率与验证记录对应最终源码；不混淆计划与结果 |

有不一致时先判断：实现偏离已确认方案则修代码；实现是已确认的新方案则修文档；实质变更尚未确认则先回到确认环节。**禁止通过删除正确要求或把错误实现写入文档来绕过验收。**

完成后记录检查者、时间、目标分支、基线 SHA、受检源码 SHA、报告与剩余问题。代码再改就重跑受影响测试/覆盖率并复查文档；目标分支更新导致合并结果变化时也重验。纯验证记录提交可以引用最近源码 SHA，并核对之后没有源码变动，避免记录自身 SHA 的循环。

## 6. 提交 MR 的出口条件

全部满足才可提交 MR（包括评审草稿）：一个任务、完整确认可追溯、feature 文档已先推送、实施范围一致、适用测试全通过、覆盖率达标、文档一致性检查通过、适用实验门槛通过、无未解决阻塞项。

使用[MR 模板](../../.github/pull_request_template.md)，填写任务目录、唯一任务 ID、确认依据、基线/源码版本、覆盖率证据和文档一致性结果。任一项缺失，继续修复或报告具体阻塞；不把 MR 当作未确认方案的审批入口。自动合并、发布和部署仍按各自授权处理，本规范不扩大权限。

原有 `tools/check_structure.py` 只检查登记的 `docs/`/`kb/` 与既有入口；`tools/check_sdd.py` 只检查 DISC 记录和指纹。两者目前都不执行分支单任务、覆盖率阈值或文档语义检查，也不递归检查 `spec/`。执行技能必须另外核对任务目录的链接、唯一范围和上述证据，不得把现有脚本退出 0 宣称为全流程合格。

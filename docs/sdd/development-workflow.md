# loom-oi 连续开发规范

## 1. 持续执行与停止边界

用户明确启动后，以完整交付已确认的loom-oi首版为目标，连续执行读取进度→选择可推进任务→补齐任务spec→实现→测试与修复→文档核对→提交/回读→阶段验证。不要在完成计划、骨架、P1或一次成功测试时自行结束整个开发目标。

| 情况 | 执行动作 |
| --- | --- |
| 已采用范围内的内部设计、分包、测试夹具、调试、必要重构、依赖下载、构建与文档同步 | 自主完成，不逐步索取许可；记录影响及有效测试 |
| 现有规格足以确定下一任务的目标、契约和验收 | 引用已有采用范围建立任务，不重复批准同一方案；实现细节自行决策 |
| 新增或改变对外契约、权限/失败语义、产品范围、验收标准，或推翻已有决议 | 先给具体方案、证据、替代与推荐，在活动Issue追加准确确认点；只暂停依赖该选择的工作 |
| 普通单测失败、编译失败、可修复工具问题 | 调试并修复后继续；测试失败不是自动转交用户的理由，不反复运行无变化的失败命令 |
| 到达阶段节点且证据满足 | 自动完成实验分析、图文/KB/Issue回写与核验，记录相应门槛后继续依赖阶段；不额外请求“是否继续” |
| 缺真实设备/凭据/资源、工具权限拒绝、无法满足的外部条件 | 先尝试适当且有授权的替代；记录阻塞及可继续任务，只向用户请求必要资源/决定，不伪造通过 |
| 发现有来源的重复探索或旧决定冲突 | 按[轻量门控](../issue-management.md#revisit-gate)追加针对性确认；已有明确重试授权则直接引用 |

普通测试与调试日志不是每轮架构讨论，不需要每次创建DISC、Issue评论或实验ITER。重要方案变化、采用和阶段实验结果才形成节点；同一节点合并回复。单元/集成测试仍保存原始输出；宣称产品阶段通过的实验按Evidence Lab规约生成可复核证据。

## 2. 单任务分支与当前任务spec

- 讨论/规则集成基线为`alpha`；一个可独立验收目标对应一个`feature/<任务ID>-<简述>`分支和`spec/<任务ID>-<简述>/README.md`。必要跨模块实现、测试、文档属于同一目标；无关功能另立任务，不把整个项目装进永久feature。
- 核对远端、工作区和现有任务ID；继续已有同任务分支，保留他人修改。按[任务模板](../../spec/_template/README.md)记录基线SHA、目标/范围、准确采用来源、适用需求及门槛、实施步骤、验收、进度与阻塞。
- 任务范围已由完整规格或明确指令覆盖时，直接沿用确认。首笔任务文档推送并回读后编码；用户明确的保存/开发授权覆盖必要提交和推送，无需逐次确认。
- 新建Draft PR不是编码前置；正式评审前完成质量与文档检查。产品任务合并遵循明确的集成授权与仓库保护规则；未获合并授权时交付可评审分支，继续独立任务，不混入未合并的独立feature，也不以“完整开发”自行部署生产或绕过评审。可在启动时一次明确集成授权，无需每次提交重问。
- 当前TASK-003仅将开发规则与G0记录集成alpha，不合并历史TASK-001/TASK-002；借鉴其有效规范时保留当前Issue只追加规则。

## 3. 确认与规格范围

采用记录支持原始GitHub评论或明确用户会话指令。会话来源保留`chat-request:<请求UUID>`、原话、日期、作者为“本会话用户”、指向的固定规格与准确差异；不猜测GitHub账号映射。AI代为发布的Issue收据只是转述，不是人类评论。已有明确采用不要求用户再去GitHub说一次。

新确认优先使用`schema_version=2`与`confirmation_ref`指向任务内唯一`approval.json`。规格以`文件#片段ID`绑定明确标记间的原始字节：`<!-- sdd-scope:ID -->`与`<!-- /sdd-scope:ID -->`各一次。批准正文包括全部必要行为、约束和验收，不能把关键参数放在片段外绕过确认。进度/状态/导航放片段外；受确认语义改变需要差异与受影响范围的新采用。旧整文件批准保留原貌，不自动重算或扩大范围。

`review`检查整份DISC；`implement --require <需求>`只检查所选需求及传递依赖的采用、指纹和关联证据，保留全局ID/引用的基本结构检查。无关Pending项和无关旧证据不阻挡本任务。G0的规格证据使用相同片段指纹。检查器只验证记录一致性，执行者仍核对原话及语义。

## 4. 有效单测与文档代码一致性

- **单元测试总体行覆盖率或语言工具等价语句覆盖率≥95%**，统计事先确定的完整受管交付单元全部自有源码，包含未执行文件。模块明细用于诊断，不额外要求每个包单独95%。不把集成/E2E覆盖率混入单测，不临时缩分母、忽略失败、添加无断言调用或修改验收凑通过。
- 对当前规则工具，受管单元为`tools/`全部非测试Python源码；实验阶段门禁属于实验验证单元，另保留回归及其覆盖报告。Go产品任务在首个任务spec固定完整产品交付单元的统计命令、排除项和报告；生成/第三方代码排除必须预先声明。
- 95%是任务完成/正式评审门槛，不要求每次中间提交或M1之前已经达标。竞态、模糊、契约、故障和资源清理测试按规格执行，覆盖率不能替代它们。
- 正式评审前逐项记录“文档章节→实现文件/符号→验证→结论”，覆盖API/CLI、默认值、权限、状态/失败、数据恢复、部署/示例与架构图。修复错误实现，不改规格迎合失败；规格确需改变时只确认受影响语义。
- 检查结果绑定源码/测试/环境和真实报告；纯文档不冒充100%覆盖。推送后回读；更改受检代码或契约后重验适用检查。

## 5. 完整交付与阶段执行

当前完整开发目标是已确认的R可信中继首版：OIS/OIC/oi、授权与准确目标绑定、PG/SQLite共同契约、观测准入、失败/恢复、可运行CLI、安装部署与维护说明、真实受支持组合及证据。不把P1纵向演示称为完整产品。

P1执行B1–B4的M1–M5；G1通过后继续P2；G2/G3/G4通过后推进P3/P4；完整单实例交付要求`release-single`对应G5/G7及所有前置通过、95%单测与相应CI通过、文档/支持矩阵一致、产物可安装复现且没有未解决发布阻塞。阶段准备可提前，依赖实施遵守实际门槛。G0不需要先写产品，G1不要求先通过G2–G7；现有门槛不增加新人工审批环。

尚未明确的后续支持组合、接口或数值承诺，先形成具体可评审方案并取得准确采用；“完整开发”不代表未定义的需求已获批准。H直连、无损迁移、HA、未经确认的MCP等支持不默认纳入。不能通过改支持范围、降低指标或只保留容易通过的组合来宣称完整交付。

现有实验runner只运行旧的机制夹具，不能直接验证Go产品。产品任务应在自己的spec内纳入真实实现测试、版本化证据采集/重算适配及必要运行器修复，保留旧run及源码快照；不能拿LAB-001/002替代G1。优先使用B4指定Linux CI生成产品证据，Windows执行能力按支持范围验证；Windows检查器修复不等于旧runner具备跨平台隔离。缺产品证据适配不阻止M1，但在G1前必须完成。

## 6. 持续进度与交付

在当前任务spec维护简短检查点：已完成/未完成、有效验证、下一步、真实阻塞、最新提交。上下文切换或恢复后先核对工作区、远端、检查点和最新人类反馈，再继续；不从头脑暴或重复重跑不变证据。实验重要结论按原规约收束回整体架构；不改已发布Issue正文/评论。

结束条件只有：本次明确目标完成；用户暂停/取消；或所有可推进工作均遇到需用户处理的真实阻塞。交付包含代码/产物入口、有效验证、支持范围、已知限制与未完成项。仅完成文档、工具自检、P1或一项门槛时报告阶段进展并继续。

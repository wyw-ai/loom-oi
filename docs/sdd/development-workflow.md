# SDD 开发流程规范

修订2，2026-11-03。保留用户四项要求：本次任务放在spec；方案完全确认后创建单任务feature并先推文档；单测覆盖率≥95%；正式提交MR评审前文档与代码一致。本轮按用户请求`3cce496f-7eee-48d4-bc53-48c1425fa72e`修复确认、任务隔离和评审阶段冲突。

[SDD总入口](README.md)负责讨论确认链，[结构规范](../structure.md)负责长期文档职责，[开发技能](../../.agents/skills/sdd-development/SKILL.md)负责执行。此修订位于feature；合入集成分支前，其他分支不得声称已采用本版本工具。用户已经明确的四项纪律不因此失效。

## 1. 一个任务的边界与文档职责

任务是一个具有明确验收边界、适合一起评审和交付的变更目标。必要的跨模块实现、迁移、测试和文档是同一目标的子步骤；无关功能和顺手修复另立任务。独立公共前置能力另立任务并声明依赖，不把每个辅助函数拆为一个任务，也不把“完善系统”当作一个无限任务。

| 内容 | 唯一维护位置 |
| --- | --- |
| 讨论过程、问题和人类反馈 | 现有Issue或明确的用户讨论入口；保留原评论及方案版本 |
| 本任务方案、实施与验证 | `spec/<任务ID>-<简述>/README.md`；复杂内容在同一目录拆分 |
| 需求采用状态及范围 | DISC JSON中的需求记录；任务只引用需求ID，不复制采用状态 |
| 可核验确认凭据 | 需求的`confirmation_ref`指向任务目录内一份`approval.json`；旧内联凭据兼容 |
| 单任务分支、目标基线、修改范围与交付证据 | 任务目录的`task.json`；README解释，不维护第二套机器状态 |
| 长期架构、模块、接口、使用说明 | `docs/`对应当前章节；spec只记录增量、引用和当时证据 |

使用[任务模板](../../spec/_template/README.md)。已结束任务的历史验证不被后续任务覆盖，现行契约以长期文档为准。任务ID在现有讨论入口登记预占，创建前核对远端分支与任务目录；不要在多个会话各自取“下一个编号”。本地检查器检测当前工作树重复ID，并不能提供跨分支的原子分配服务。

## 2. 确认前保存方案，确认后建立开发基线

确认前可以编写任务草案、调查和验证方案，不提前建该任务的feature或实施产品代码。评审方案保存到已有讨论入口，使用完整方案评论的固定链接/版本，或可读取的固定版本附件；可变的Issue正文只导航到当前方案。长文不能只留在作者本地工作区。

用户直接在会话中确认时，保留原始请求ID、日期、原话及其指向的方案上下文；落库时核对内容，不把AI补充的未决选择记为用户批准。明确且完整的用户指令可直接作为确认，不机械重复询问。若指令只确认原则，方案中新增加的实质取舍仍需确认。

“完全确认”限于本任务的目标、范围、对外契约、关键选择和验收；不要求整个项目所有问题收束。合理的内部实现细节可在此边界内决定。部分确认只解锁完整确认且可以独立交付的任务，不能借拆分绕过依赖。

确认后从约定集成分支最新提交创建`feature/<任务ID>-<简述>`，记录目标分支与基线SHA。首笔提交只包含任务文档和必要规格/导航，推送并回读，与已确认方案版本逐项核对一致后才开始实现。用户原有工作区改动先隔离，不丢弃、不混入本任务。本任务修订2的文档先行提交为[9ea8abb](https://github.com/wyw-ai/loom-oi/commit/9ea8abbd03daec0f966bd01c9b01b7648c188b8a)。

## 3. 统一确认记录与规格片段

`check_sdd.py`兼容旧schema_version=1；schema_version=2支持`confirmation_ref`和明确的规格片段。确认记录包含author、date、source、scope和fingerprints；source支持`github_comment`的原评论链接，或`user_instruction`的`chat-request:<UUID>`及原话。示例见本任务[确认凭据](../../spec/TASK-001-sdd-workflow/approval.json)。原文身份、上下文和授权仍须执行者实际核对，合法JSON不能凭空创造批准。

Issue仍承担项目的讨论与任务追踪入口，DISC及需求仍须映射真实Issue；聊天确认免去的是重复索取GitHub确认评论，不是取消追踪记录。已有明确聊天批准时直接沿用，补齐关联即可，不重新要求用户批准相同方案。

新增规格使用`路径#片段ID`作为fingerprints键，文件内只允许一对明确标记：

```markdown
<!-- sdd-scope:interface-R1 -->
这里是本需求被确认的行为、边界和验收，不包含进度或运行结果。
<!-- /sdd-scope:interface-R1 -->
```

哈希只覆盖标记之间的原始字节。标记外的进度、其他章节和链接调整不影响此批准；标记内变化不会自动继承旧批准。格式性调整可放在标记外；确需改动受确认片段时，保留旧版本、说明差异并核对确认，不能自动重算批准哈希。缺失、重复、空片段和路径越界均拒绝。

旧整文件凭据保留原貌，不自动迁移为更宽范围；已批准的旧文件变化时仍需核对原批准。新任务优先采用任务独立片段，长期共享文档由任务影响分析负责核对。`review`检查整份DISC；`implement --require ...`只检查所选需求及传递依赖的指纹、采用和证据，不能被无关需求的过期文件阻塞。全局ID和基本结构仍须合法；不允许漏掉真实依赖。

同一任务内改变接口、权限、失败语义或验收，先更新受影响方案并确认，再继续相关实现；无关任务的确认不受影响。实现错误应修代码，不能静默改需求迎合错误行为。

## 4. 单任务分支与并行开发

一个工作分支绑定一个任务，一个MR交付该任务；合并后不复用分支承载新任务。集成分支可汇集已合并历史，不在其上继续直接开发多个混合任务。范围按相对目标基线的差异判断，已有基线历史不算本任务改动。

`task.json`声明唯一ID、branch、base_branch、base_commit、manifest、requirements和allowed_paths。检查器核对目录/分支绑定、当前工作树重复ID、修改其他任务目录及超出声明范围的文件。路径白名单只能发现明显混入；是否存在第二个业务目标仍由评审判断，不能靠扩大白名单绕过。

只同步集成分支的已合并变化；尚未合并的独立feature作为依赖等待或协调，不直接混入当前MR。目标分支前进时先读取新规则、保留双方变更并解决冲突，更新基线和受影响测试/文档证据。禁止把feature旧文件整份覆盖最新集成规则，禁止自动刷新已采用凭据。

## 5. 单元测试覆盖率≥95%

所有代码任务的单元测试必须通过。使用项目预先确定的受管交付单元，统计其**全部自有源码的总体行覆盖率或语言工具等价的语句覆盖率，至少95%**，包含未执行文件。模块明细用于诊断，不额外规定每个模块分别95%。

统计根目录、指标、固定排除项和命令在方案里明确。只使用单元测试报告；集成/E2E报告分别记录。不得临时排除难测业务代码、缩小分母、忽略失败测试或添加无有效断言的测试凑数。正常、边界和失败行为仍须有效断言，覆盖率不替代正确性。

现有基线不足时如实记录：若补测属于当前行为修复的必要子步骤，在当前任务完成；若是独立历史治理，另建前置任务并完成，不能夹带进无关功能或降低95%门槛。

当前代码变更属于仓库工作流工具，统计范围固定在[coverage-policy.json](../../tools/coverage-policy.json)：tools目录全部非测试Python源码。测试代码不计覆盖分母，但计入证据源码指纹。实验及未来OIS/OIC产品使用各自完整交付单元验证；工具覆盖率不能证明产品达标。新增语言/目录未被当前策略覆盖时检查器拒绝，应先建立相应测试和统计策略。

记录实际测试命令、工具版本、环境、原始报告、分子/分母及源码/测试/策略指纹。缺报告、报告遗漏源码、分母不一致、覆盖率不足、测试失败或指纹过期都阻塞正式评审。单纯文档/技能文字且不改变可执行、构建或运行行为时，注明覆盖率不适用及diff依据，禁止写成100%。

## 6. Draft、正式评审与合并分开

| 阶段 | 必须满足 | 仍可未完成 |
| --- | --- | --- |
| 创建Draft MR | 本任务完整确认、文档已先推送、唯一任务及范围可追溯 | 开发、覆盖率、文档一致性检查；明确列为未通过/未运行，允许CI在此运行 |
| 转为正式评审 | 实现完成，单元测试通过且覆盖率≥95%，文档代码一致，适用实验条件满足 | 评审意见尚未产生；剩余风险如实说明 |
| 合并 | 正式评审通过、最终源码和目标基线检查有效、获得相应合并授权 | 不允许未解决阻塞 |

Draft不是方案批准的替代，也不等于可以合并。新评审意见导致实质方案变化时回到对应确认范围；代码或目标基线改变后重验。使用[MR模板](../../.github/pull_request_template.md)，不将“创建MR”一概视作“请求合并”。本轮用户只要求同步修订与保存，不自动创建MR、合并或部署。

## 7. 正式评审前的文档代码一致性

按最终diff逐项记录“文档章节→实现文件/符号→测试或核验→结论/修正”，覆盖需求验收、API/CLI、配置默认值、权限/状态/失败、数据迁移、部署/示例、架构图和导航。无影响项给具体理由；不能只勾“文档已更新”。

实现偏离已确认方案则修代码；已确认方案变化则同步文档；未确认的新行为先回确认。记录检查者、日期、基线、受检源码指纹和可读取的核验结果。语义一致性由评审负责，能自动验证的契约/示例使用测试支撑；字段齐全和检查器退出0不代表语义正确。纯记录提交不改变源码时无需制造自引用提交SHA。

## 8. 本地检查与能力边界

```bash
python tools/check_structure.py
python tools/check_sdd.py docs/changes/DISC-003.json --phase implement --require DISC-003-R1
python tools/check_task.py spec/TASK-001-sdd-workflow/task.json --phase draft
python -m coverage run --source=tools --omit='tools/test_*.py' -m unittest discover -s tools -p 'test_*.py'
python -m coverage json -o spec/TASK-001-sdd-workflow/coverage.json
python tools/check_task.py spec/TASK-001-sdd-workflow/task.json --phase review
```

测试完成后在task.json写入真实执行信息和`check_task.source_digest(root)`的返回值，文档核对记录使用相同源码指纹，并记录check_task.documentation_digest对当前差异中文档的指纹（排除task.json、核验记录本身和coverage报告，避免自引用）。文档在核验后改变也必须重验；检查器不替执行者运行测试或核实原话。结构检查已递归覆盖spec的Markdown链接；任务检查核对当前工作树和集成基线、范围、确认及coverage.py原始报告。它不是通用语言覆盖率解析器；其他工具须建立适配后使用，不伪装为coverage.py报告。

CI与远端分支保护尚未部署；这些是已可执行的本地门禁，不声称服务器会自动阻止违规合并。执行前先同步远端引用，CLI不能证明本地alpha引用永远最新。原有实验门槛、Issue原评论回应和成员权限规则继续适用。

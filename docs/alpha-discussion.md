## 2. 净化后的讨论脉络

### 2.1 从“文档太大”到“核心不碰业务”

13:00 起，[已脱敏] 指出原稿把 Agent 管理、多 Agent 协作和工具管理混在一起。14:28 起提出专注受控端；14:35—14:36 双方认可底层能力连接与业务分开。

最初的分歧并非“是否做 Agent 平台”，而是如何保持通用、轻量和独立：一方希望复用 Loom daemon、降低部署负担；另一方担心把 Actor / Channel 等带入 OI，破坏其作为独立能力通道的价值。单仓还是独立部署没有形成决议。

### 2.2 把“工具管理”澄清为“能力登记”

14:53—14:59，[已脱敏] 反对把模型、Runtime 和 MCP 平台管理放进 OI。Hansion 进一步解释，其意图是 Node 登记能力，“其实只是注册而已，不是server自己的工具”（L573）。这解决了一部分术语误会，但没有决定 OI 是否需要统一解析工具调用。

15:05—15:07，双方明确不由 OI 管 Agent Session，且 Magpie 不耦合进入核心。旧文档的执行平台职责因此缺少成立依据。

### 2.3 网络路径与能力调用抽象交织

15:10—15:19，一方倾向 OIS 中转、统一入口；另一方倾向节点间直连，关注内网直达、延迟和原生协议。双方都认为 OIS 参与连接协调，但没有决定所有数据是否经过它。

15:32 的具体调用例子很有价值：发现工具 → 选择目标 → OIS 查路由 → OIC 本地分发 → 用户能力执行。这说明一方期望 OI 具备可直接使用的能力调用入口。16:07—16:09 Hansion 的“洞里走什么是业务定的”则更接近透明能力通道。两者都不碰业务规划，却对协议适配投入有不同要求，不能因同意“不碰业务”就视为同一个设计。

### 2.4 Workload 争议实际包含三件事

第一是命名：Node 有时指工具包，有时指宿主；Workload 的对应位置也变化。第二是运行边界：能力是否可独立启动、故障是否互相影响。第三是调用者隔离：不同 Agent 是否共享桌面、浏览器等资源。

15:24—15:29 双方承认 extension / node 有部分语义重叠，并讨论进程隔离。15:58 [已脱敏] 给出一套映射；16:03 Hansion 又明确其理解为 Node 对应宿主、Workload 应拆开。16:05 对方承认仍在套用现有概念、尚未归纳自己的层。因此没有“已统一的 Node / Workload 定义”。

### 2.5 “无状态”的诉求与隔离的担心都要保留

[已脱敏] 希望避免按 Agent Session 分配连接和资源，由工具实现方管理业务状态；Hansion 担心多调用者干扰及共享故障。15:56 对方认可前者有道理，同时明确还要找平衡方案。这是继续讨论的信号，不是删去所有状态和隔离机制的确认。

### 2.6 可验证的消费场景出现

16:21—16:24 明确小规格跳板机只需部署 OIC。次日 11:10—11:12 提到 Hook 触发 Agent、上下文管理、虚拟手机承载微信/QQ，并明确依赖 OI。它提供了“连接真实个人资源”的测试场景；Agent 上下文仍是上层需求。

新闻收集、自定义 App、手机说话生成程序等讨论有助于理解能力消费方式，但不足以要求 OI 自建新闻平台或动态 UI。MC 服务器搬运、模型额度、聊天工具使用及日常闲聊过滤出架构输入；游戏能力独立接入的例子则保留。

## 5. AI 推演与专业建议

以下均为 AI 新增，用户尚未确认。

1. **把调用抽象与网络路径分开。** 同一个工具适配层可以复用直连或中转；透明协议也能经中继。这样无需为了讨论 P2P 同时决定所有工具语义。
2. **区分身份、部署实例、能力声明和连接。** 先拿电脑、外部 HTTP 服务、虚拟手机三个实例测试映射，再定 Node / Workload 名称。层级存在应有独立的配置、生命周期或故障边界理由。
3. **保留管理/通信状态，避免统一业务 Session。** 提供方需要任务或资源句柄时显式暴露。连接恢复只恢复通信，不能承诺恢复任意 Agent 执行。
4. **授权不等于资源锁。** 网络可达、访问许可、某个桌面的独占权分别处理。资源 ID 和独立流不会自动提供隔离。
5. **能力实现优先可独立运行。** 可选子进程托管与通用部署调度要分开讨论；不要为了轻量只用进程内插件，却隐瞒共享崩溃边界。
6. **先做非 AI 的调用闭环验证。** 脚本能够使用 OI，是验证核心独立性的直接办法。用户后续已明确暂不接 Loom；虚拟手机仅作架构反例，非当前集成承诺。

这组建议不是折中方案已经胜出。尤其“透明通道 + 可选适配层”会增加层间契约维护，需要用户判断其便利性是否值得投入。

技术校核已写入[状态与隔离](distributed-architecture-conclusions.md#5-状态与隔离)：MCP 2026 的协议无状态说法有依据，但应用状态、流式响应和连接管理依然存在；UDP / P2P 也不自动提供业务或进程隔离。

# 文档结构与引用规范

本页定义内容放置与维护责任；Issue正文规则见[Issue规范](issue-management.md)，批准和实施链见[SDD](sdd/README.md)。入口为[文档导航](README.md)，全量清单由[结构登记表](catalog.json)生成[目录](catalog.md)。维护这些规则的Issue单独承载治理，不覆盖产品取舍。

## 内容职责

| 读者要解决的问题 | 唯一维护位置 | 其他位置可以保留什么 |
| --- | --- | --- |
| 从哪里开始、下一步看什么 | 根README、docs/README、各域索引 | 一句用途与链接；不复制当前选择、实验状态或变更日志 |
| 项目为何存在、为谁承担哪些一致能力 | docs/concept/loom-oi.md；组件概念在同目录 | 项目承诺/边界与共同理念，组件从中推导；参数和机制指向架构 |
| 组件如何协作、共同契约是什么 | docs/architecture/alpha-v0.7.md | 模块页索引对应契约，只细化本模块，不另定义相同字段 |
| 场景怎样使用当前架构 | docs/designs/application-paths.md | Issue保留足以判断的部署、正常/失败链和取舍摘要 |
| 本轮改了什么、来源和确认覆盖哪里 | docs/changes/DISC-NNN.md/.json | MD是变更说明和证据定位；JSON是范围/指纹/任务/验证，不复制完整方案 |
| 为什么已选某个重要方案 | docs/decisions/ADR-NNN-*.md | 一个决定及准确范围；kb/decisions只做决议索引及授权台账 |
| 现在需要讨论/确认什么 | GitHub Issue初始快照＋阶段评论 | 发布后只追加；阶段方案自足，当前阅读入口指向明确阶段，旧正文/评论不删除 |
| 为什么走到这里、旧方向为何停止 | kb/lineage及docs/issue-history | 类型化阶段关系、可取得的原文快照与固定版本；事实缺口不补造 |
| 依据从哪里来、可信到什么程度 | kb/evidence、kb/conclusions、docs/evidence、experiments | KB记录来源/窄结论及回链，报告保留当时版本和局限，不反向覆盖当前规范 |
| 怎样维护以上工作 | AGENTS→项目skill→规范/模板/检查器 | skill负责操作顺序；规范负责格式/含义；避免三处复制同一长规则 |

显示名称统一中文，内部机器映射见[vocabulary.json](vocabulary.json)。角色并非批准状态。架构页可以是当前有效的评审中草案；ADR的已采用只覆盖原回复明确范围；历史报告不因目录位置变成当前契约。

## 当前正文与历史

1. **仓库当前规格**在对应章节整合现行结论，历史由Git追溯；**已发布Issue正文/评论**按[追加规则](issue-management.md#append-only)保留，新增阶段解释变化。两种载体不能共用覆写规则。
2. Issue开头两句说明问题和推荐；长推导归设计/证据页，但正文必须有可判断的机制、失败例和代价。仅缩短或仅加链接都不算整理。
3. DISC保存来源、变更摘要、稳定需求/验证映射及必要交付记录；不同时保存架构和应用设计的完整副本。小变更可以继续共用一个DISC，不为格式增加空文档。
4. 仓库文档不另建archive副本，旧版本用固定commit链接。Issue平台原文并非Git天然保存；docs/issue-history的实际快照与实验raw/来源记录同属证据，不当冗余旧文档删除，不补造缺失历史。
5. 现有外链锚点迁移时保留简短跳转；兼容入口只导航，不继续写第二份当前方案。新增链接应直达权威正文。

## 引用关系

每条跨产物关系写清类型和理由；“相关链接”不能代替依赖说明。

| 类型 | 含义 | 用法 |
| --- | --- | --- |
| 依据 | 提供原意、事实或明确决定 | 指向原文、固定提交或具体评论；说明支持哪一判断 |
| 规格 | 某问题的详细契约在何处维护 | 指向当前稳定路径和明确锚点 |
| 验证 | 哪个验证覆盖哪条承诺 | 说明所测范围，计划与通过分开 |
| 依赖 | 缺少上游结果就不能完成某项下游行为 | 写阻挡的是设计、实施或交付；不把一般相关项变成审批环 |
| 承接 | 父项/条件单承接一个工作范围 | 不重复作出被承接单的决定 |
| 替代 | 新版本替代某旧结论的准确范围 | 旧证据不删除；用固定版本保留原貌 |

规范性内容只定义一次，关系不要求机械对称。目录→正文可单向；Issue→规格、DISC→Issue须可追踪；每个强依赖必须有理由且不能成环。索引可引用当前路径；原始证据、阶段确认和历史比较用固定版本/评论ID，动态分支链接不证明当时内容。引用冲突时回到原文/最新明确确认核对，不按链接数量投票。

## 维护与检查

新增/删除/改变用途的文档同时更新catalog.json，运行`python tools/check_structure.py --write-index`生成目录；普通正文编辑无需重复改元数据。登记表只保存路径、角色、用途与必要关系，不复制时间、状态或正文哈希；SDD继续独立维护需求指纹。

运行`python tools/check_structure.py`核对当前文档覆盖、路径/锚点、目录生成一致性、规范主题唯一性和强依赖环。给`--issues <临时GitHub快照.json>`检查本轮Issue的六节结构与正文引用，快照不提交仓库。脚本不联网，不判断人类批准、语义完整性或产品正确性；仍需按技能做只读内容评审、SDD与远端回读。

# alpha 首轮隔离实验：观测、反证与边界

2026-11-02（+08:00）。本报告连接原始证据与架构影响；没有 OI 实现、生产网络或语言性能结论。[实验入口](../../experiments/README.md)。

## 实验条件

运行前固定 manifest、对照、故障点和5次重复；种子决定顺序。Python标准库HTTP fixture 仅绑定回环地址，故障注入由实验服务控制。两组均正常退出，原始数据和摘要可重算。环境/源哈希随run保存，父级提交 beaef2d 只是开始基线，实际执行代码由 source-manifest.json 的哈希标识，随本轮提交保存。

隔离是受信进程级：独立工作目录/环境/进程组、CPU/内存地址空间/FD/文件上限、30秒超时。user/network namespace不可用，不能声称强沙箱；没有执行不可信插件。环境8GiB/8CPU额度，不是目标1C1G机器。没有 NAT、TLS、MCP、OIS/OIC 或真实设备参与。

## LAB-001：TCP 可达、业务就绪和探测调度

原始输入/观测：[manifest](../../experiments/runs/LAB-001-20261101T191556Z-7863f9/manifest.json)、[raw](../../experiments/runs/LAB-001-20261101T191556Z-7863f9/raw.jsonl)、[环境](../../experiments/runs/LAB-001-20261101T191556Z-7863f9/environment.json)、[重算结果](../../experiments/runs/LAB-001-20261101T191556Z-7863f9/summary.json)。

设置三类 HTTP 目标：正常200、未就绪503、处理延迟150ms而socket等待超时50ms。各重复5次；另比较同样目标/socket超时条件下，串行探测与最多2个工作线程独立调度。50ms约束单次阻塞操作，并非整个调用的deadline。观测时间是测试夹具的完成时间，不是网络/产品延迟承诺。

| 实际观测 | 数值 | 可支持的窄结论 |
| --- | --- | --- |
| TCP成功但业务503/超时 | 10 / 15 次 | 其中明确503为5次、超时未知为5次；端口可达不足以证明及时应用成功。这是构造反例，不是故障概率 |
| 串行策略健康目标完成时间 | median 51.666ms；范围 51.517–52.108ms，n=5 | 同轮健康目标会等待前一个慢请求触发socket超时 |
| 独立调度健康目标完成时间 | median 3.105ms；范围 2.180–4.137ms，n=5 | 在这套局部调度器里可避免该顺序等待；不证明OIC全局公平性 |
| freshness模型行 | 5条，排除于实测统计 | revision失配/心跳不续期只是规则示意，未执行真实分布式状态测试 |

机制解释：对照的 TCP 层仍建立连接，HTTP 层独立返回未就绪或触发socket超时。串行/独立调度改变了健康请求何时启动。不能把刻意构造的比例解释为真实服务失败率，也不能拿时差给生产 p99 或 Go/Rust 排名。

影响 #2/#7：请求完成观测为避免串行等待提供机制依据。全局额度、状态独立发布、全目录故障隔离及freshness字段仍是待实现和验证的设计建议。建议增加probe_support、探测来源、observed_at、有效期、配置版本，分别表达接入在线、目标可达、业务就绪、资源忙；其中资源忙也没有本轮实验的直接支持。上述建议尚非OIC实现验证。

## LAB-002：响应丢失后的副作用

[manifest](../../experiments/runs/LAB-002-20261101T191558Z-270709/manifest.json)、[raw](../../experiments/runs/LAB-002-20261101T191558Z-270709/raw.jsonl)、[环境](../../experiments/runs/LAB-002-20261101T191558Z-270709/environment.json)、[重算结果](../../experiments/runs/LAB-002-20261101T191558Z-270709/summary.json)。

服务接收 POST 后先递增计数器，再在发送任何响应前断开；客户端随后通过独立 GET 观察计数。每次策略试验先复位；两策略各5次，顺序随机化。

| 策略 | 客户端观察 | 独立查询到的计数 |
| --- | --- | --- |
| 不隐式重放 | 请求收到连接/响应异常 | [1, 1, 1, 1, 1] |
| 盲目重放一次 | 两次请求均收到连接/响应异常 | [2, 2, 2, 2, 2] |

结果证明这个受控故障下，“客户端没收到成功”与“服务未执行”不同，额外重试会额外执行。它不证明所有重试都不安全，也没有验证带持久幂等键的服务。fixture通过代码显式发送一次或两次mutation请求，比较不重放与重放一次的效果。

影响 #4/#6：图和契约继续把通道中断与业务结果分开；传输恢复不隐式重放。业务状态查询/去重必须由提供方或有证据的适配契约提供。没有模拟 Exactly-once 或跨节点事务成功。

## 独立复核、修正与保留

独立只读审阅者只收到技能规约、manifest、源代码、环境、execution和raw，没有先读取本报告、summary、KB或推荐。它复算了首轮25条机制观测行与5条模型行、10条副作用策略记录；确认试次覆盖、退出状态和源码哈希，同时指出下列问题：

1. 首版摘要把503与超时合称“not_ready”，范围过大。现拆成explicit_http_503与timeout_outcome_unknown；原始数据和旧摘要保留，新版manifest/分析器重新运行产生新run，本报告使用新版结果。
2. 健康请求完成计时不代表健康状态已经发布；fixture仍等慢请求结束后才emit。本报告只主张请求完成时间差，不声称状态发布隔离已验证。
3. freshness_model是固定模型行，不是TTL/revision实现测试；继续排除。
4. 首版自动分析没有验证唯一试次键与attempts一致性；本次原始数据经独立核对没有问题，分析器已补检查并加入反例测试。
5. 同一进程/监听端口、sleep故障、未排空handler、仅内存计数限制外推。不能称持久事务、进程隔离或五次独立部署；后续规模/饱和/持久化实验另立契约。

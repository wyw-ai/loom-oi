## 2. 从整体目标检查质量

| 维度 | 已有设计基础 | 具体缺口与失败链 | 当前判断 |
| --- | --- | --- | --- |
| 高正确性 | 准确绑定、版本分离、最终准入、Unknown/NotReady区别、不重放 | Open检查策略后发生撤销、另一数据腿迟到，何处原子提交/拒绝仍需R6定义；旧票据并发附着、FIN顺序及过期后回收需实际状态机验证 | 原则充分，接口和竞争规则尚不足以让不同实现者写出一致行为 |
| 高可用与恢复 | 有限许可、失败可解释、新通道重建；主备候选单列 | 当前R经OIS；OIS/宿主、PG或入口失败均可影响全链。单实例自动重启不是跨故障域HA，PG副本也不自动保护OIS权威/入口；未定SLO、故障模型与恢复窗口 | 单实例恢复路线可继续细化；不能承诺HA、无损续流或某个可用性百分比 |
| 高可维护性 | 核心不接管业务；模块职责、单一共同契约、Git/SDD及追加历史已建立 | 无产品包/依赖锁定、数据库迁移版本、协议兼容规则、构建CI与操作手册。两后端若各自解释Conflict/提交成功，会形成维护分叉 | 结构合理；工程约束要落到首个任务和同一组后端契约测试 |
| 安全与资源边界 | 本地允许项、认证、角色绑定、有限许可、控制/数据分开 | 证书主体映射/轮换、票据一次消费、DNS目标重绑定、慢连接/超大消息以及数据库拥塞下撤销仍缺实现契约与测试 | 是P1安全骨架及P2/P3验证范围，不能被“通道透明”省略 |
| 可验证与可运营 | G0–G7、窄机制证据及R1/R2物料可复用 | 目标版本/拓扑、初始配置上限、失败判定与观测点未固定；日志/指标尚无实现 | 可准备可重复验收；没有产品通过证据 |

以上为本项目审查推论。官方资料仅约束局部机制：[SQLite WAL](https://www.sqlite.org/wal.html)要求同主机共享内存且长读可延缓检查点；[PostgreSQL复制](https://www.postgresql.org/docs/18/warm-standby.html#SYNCHRONOUS-REPLICATION)中异步切换存在已提交事务丢失窗口，同步配置有耐久性/等待代价。两者均不证明OI恢复任期不会回退。Google的[SLO方法](https://sre.google/workbook/implementing-slos/)支持从使用者体验定义少量可靠性指标，不能替本项目选择数值目标。上述来源本轮已核对，未新增选型。

## 3. P1前只收束这四组事项

以下是AI建议的最小实施规格包，**尚非新增产品采用**。由现有#3/#4/#11/#15共同承接，同一份任务一次整体评审，不分裂成多轮逐字段求批。详细契约继续归共同架构；此处是缺口定位和建议出口。

| 事项 / 归属 | 已存在的依据 → 尚缺内容 | 建议的最小可评审产物与判定 |
| --- | --- | --- |
| B1：协议与状态机 / #3 | §3–7给字段/消息草图，但没有完整线格式、版本兼容、消息大小与错误映射 | 固定v1最小消息/配置schema、必填/未知字段行为、DATA/FIN/ABORT编码及状态转移表；明确Open去重键/参数一致性/过期。用“撤销与提交竞争、旧代清理新代、半关闭后迟到DATA”向量约束实现 |
| B2：授权与目标安全 / #3 | mTLS、短票据、本地目标及期限是建议，最终提交和一次性消费的原子边界未定 | 声明认证主体→Access→角色/Channel/目标的校验点；票据只能一个附着消费，失败重试规则明确；目标解析/拨号必须保持允许地址边界，禁止任意URL/重绑定绕过；定义控制失联、长暂停与过期的停止行为 |
| B3：存储与重启 / #4 | C2已选部署/迁移范围，但事务、恢复代数和迁移失败出口未冻结 | 给PG/SQLite共用接口及冲突/耐久性契约、最小表/索引与schema版本；配置/版本/审计同事务。说明旧备份恢复后的旧票据如何失效，可比较持久恢复代数与新运行实例标识；切换前验证失败留原权威，切换后不能直接回旧库。此处先解决单实例，HA算法留G6 |
| B4：首个任务与验收基线 / #11、#15 | 已定OIS/OIC Go与R；具体CLI、驱动、目标平台、运行参数和判定尚缺 | 锁定首个非生产验证平台/Go及驱动版本，给可重复构建、CI与两个后端同契约用例；为并发、消息、准备期限和清理设置明确初始配置及失败断言。初始值是测试配置，不是1C1G容量或生产SLO；实验再校准 |

建议首个任务只覆盖：**一个OIS、两个逻辑上明确区分的OIC/目标、一个消费者，R通道、两个存储后端分别运行同一验收**；两个目标用于验证A1→B1/C1→B2不串路，不声称两个进程等于主机隔离。部署A同进程分模块作为低复杂度建议，不因此批准独立扩展部署。CLI若仅为验收客户端，可先明确最小消费入口，不因未定完整公共SDK阻塞核心契约。

该任务的出口应同时覆盖正常读取、拒绝未授权/错目标/旧票据、准备超时、重连不复活旧流、异常清理和两后端元数据一致性。P1需实现安全所必需的基本拒绝/期限/清理；P2再扩展完整观测、故障与饱和矩阵，不能把授权/资源边界全部推迟到P2。单测覆盖率按适用开发约定执行，并辅以契约/集成、Go竞态检测和协议解码模糊测试；覆盖率不能单独证明并发或恢复正确。

## 4. 哪些可以现在做，哪些在实现后验证

| 当前动作 | 判断 / 理由 |
| --- | --- |
| 整合B1–B4任务规格、接口样例、失败向量、测试数据和受控环境计划 | 可以；已定方向内的独立设计与准备，不需要再选Go/C1/C2/C3 |
| 宣布P1产品实施已获完整放行 | 不可以；先完成B1–B4的准确范围评审与G0记录。G0不是必须先有产品性能数据 |
| P1实施后验证G1，再进入P2 | 推荐路线；避免“没有实现所以无法实验、没有所有实验所以不能实现”的循环 |
| 真实观测/传输/双库恢复、容量及应用兼容 | 分别在G2/G3/G4、G5、G7验证；不用将所有未来样本作为P1入口 |
| 主备与H/M | H按C3可继续研究/准备；H实现范围和验证另定。HA承诺必须额外满足G6；M未纳入。它们不阻挡R单实例闭环 |

若“首版上线必须跨主机高可用”成为硬要求，则它与当前C2单实例交付边界不同：应在#4/#17明确调整故障域、RTO/RPO及部署范围，形成可审阅方案后再实施。不能靠多放一个副本或改变标签满足该要求。本轮把高可用作为评估维度，不擅自推定用户已改选首版范围。

## 6. 整体收束与局限

三项选择共同保持“接对获准目标、失败可解释、能力独立演进”。C1扩大的是Unknown时允许尝试的机会，C2明确的是首版故障与维护范围，C3限制的是路径演进粒度；它们互相不能补出HA或业务成功保证。建议以R单实例完成正确性闭环，再用真实资源/恢复数据决定后续部署与路径投入。

本轮同步采用记录、共同架构/模块、图中状态、G0阻塞描述及Issue阶段。图只更新采用/未验证标识，不增加部署能力。当前没有依据给“开发准备度80%”或“高可用评分9分”之类汇总分；用明确缺口和阶段出口判断，比无实测评分更可执行。

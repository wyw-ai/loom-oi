## 2. 观测契约：进一步修正状态图

C01排除了online即ready，但没有替我们实现状态机。当前推荐下列设计，均待实现验证：

- 将`probe_support`、`probe_execution`、`readiness_observation`分开。Unsupported是能力描述；Idle/Running是检查执行状态；Unknown/Ready/NotReady是有时效的就绪判断。周期检查开始不应自动抹掉仍有效的旧观测。
- 保存最近一次尝试及最近一次有效观测。一次超时/权限不足写入attempt原因；不伪造NotReady，也不为旧样本续期。旧证据按其原有效期及目标版本判断；到期、目标revision变化或来源失效后成为Unknown。明确的较新正/负证据可替换旧判断。
- Observation草图包含目标、来源、探针契约版本、目标revision、采样顺序/时间、有效期、结论及原因。接入generation用于拒绝旧连接写入，不伪装成服务重启代数；跨主机时钟差及有效期计算还需单独定义，不能仅比较未校准墙钟。
- 准入策略独立于观测。Unknown不证明可用，也不证明故障；严格消费者可要求有效Ready后才准入，允许尽力访问的消费者可在授权/资源约束内尝试原协议。默认策略和适用场景交#10/#3决定，不能由监测布尔值暗中决定产品承诺。
- 推荐有界并发、每目标一个在途探针、独立结果发布和有界遥测导出。代价是队列、公平性、采样过期处理；不先引入进程池或无限线程。C02只支持避免这套fixture里的串行等待，不能证明这些机制已有效隔离控制面。

正常轨迹：Ready仍在有效期内 → 周期检查Running → 新成功样本替换旧样本。反例轨迹：Ready → 检查超时且旧证据仍有效 → 保留带年龄的旧观测并报告本次超时 → 到期Unknown；不能把“探测中”当服务失败，也不能无限沿用旧Ready。以上为纸面推演，没有增加实验数据。

## 3. 失败契约：恢复连接与恢复业务分开

| 条件 | 内核可报告和执行 | 不得推断 |
| --- | --- | --- |
| 权限/目标校验拒绝，且能证明本次尚未向目标转交载荷 | 本次Open拒绝，释放本地资源；后续申请重新鉴权 | 其他通道或之前尝试未执行 |
| 已向目标转交部分载荷，或无法证明未转交 | ChannelInterrupted，携带可核实的传输阶段；允许重新建连但不自动重发旧业务 | 操作失败、未执行、已撤销或可以安全重试 |
| 原生消费者能证明操作幂等，或提供方具备已验证去重/结果查询契约 | 由该语义层在预算内决定重试/查询，处理键作用域、有效期及崩溃恢复 | 增加request_id就获得Exactly-once，或不重放就保证端到端At-most-once |

这里“不重放”指失败后在新调用/通道重新提交业务。可靠传输协议内部的丢包恢复属于不同层；[RFC 9000 §13.3](https://www.rfc-editor.org/rfc/rfc9000.html#section-13.3)明确传输信息的重传机制，不应被本条禁用。[RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)对非幂等自动重试施加条件；这是协议依据，不是本项目已经选QUIC或实现了重试控制。

代价：遇到结果未知时不能自动掩盖错误，需要调用方查询、重试策略或人工处理。收益：不靠通用连接器猜测不可见的业务副作用。反例：只读或真正幂等的请求可以有安全重试；它推翻“所有重试都危险”，不推翻“无语义证据的内核不能通用重放”。

## 4. 整体方案如何收敛

| 方案部分 | 本轮取舍 | 为什么 / 何时改选 |
| --- | --- | --- |
| 共同内核 | 推荐登记、受控目标、鉴权连接、有界资源与可核实传输结果 | 与H1和连接诉求一致；C03限制失败保证。具体协议和产品实现仍未批准 |
| 观测扩展 | 推荐可选协议探针/提供方观测，保留来源；不默认拥有服务启停 | C01否定单一online；桌面/设备/stdio有不同支持与成本。若产品要求OI托管，另承担生命周期责任 |
| 消费入口 | A作为原生连接验证基线；仅当真实消费者需要统一语义时选择B/C | 两组实验没有比较消费产品价值；不能把共同内核等同于批准A或默认建设C |
| 路径与可用性 | R仍为有条件的首条验证路径；不据C03宣称它优于D/H | 内网直达、保密或中心失联要求会改变选择；恢复新通道不等于恢复业务会话 |
| 语言 | 保留Go统一核心的当前建议，明确不增加实证强度 | 资源/维护/嵌入证据可能转向Rust；现有实验无法区分语言 |

因此可以推进共同状态与失败接口的评审，无须等全部产品问题解决；但“要不要统一Invoke、是否托管、可用性承诺、路径/语言采用”仍是真实取舍，不能借实验越权冻结。

## 4. 对 #13 的重新求解

### 4.1 先保留A1→B1、C1→B2，再判断真实资源是否共享

**推荐不变量**：每次Open绑定`主体 + Access + Exposure + revision + 当前代数 + 许可 + Channel`；之后载荷只交给这次获准目标。两路即使共享OIC/OIS进程或将来共享传输池，也不合并主体、目标、权限和字节流，不按“最后一次选择的目标”转发。目标不可用则给本路失败；不自动改投另一个同名/同类型服务，不重放在途内容。

| B1/B2实际含义 | 具体方案及所有者 | OI能保证/不能保证 |
| --- | --- | --- |
| 两个独立可寻址服务/工作面 | 外部部署者创建并拥有B1/B2；配置两个Exposure，A/C各选获准目标；OI分别拨号/关闭 | 可承诺准确路由与通道隔离的契约；不能只因两端口就宣称进程/桌面独立，需核验资源 |
| 同一服务内部的两个tab/任务/资源句柄 | 原协议两端携带并校验各自句柄，服务持有业务映射；OI只传输 | 不读取业务ID来分资源；若服务分辨不了B1/B2，增加OI通道不会创造它们 |
| 同一不可并发操作的真实桌面/设备 | 外部提供方串行/拒绝/提供独立工作面；确需共享才采用r3有限回合和静止后交接 | 互斥是该业务组合的支持条件，非全部Exposure的核心必装协议；原始旁路须纳入同一权威 |

正常推演：A选择B1、C选择B2，B1服务退出只使B1访问失败，B2不被目录删除或改路；但共享OIC进程整体退出仍可同时中断两路，不能说“一路炸绝不影响另一路”。反例：两个Exposure背后都是同一桌面，则先识别为第三类，不能因图画成两条线便声明互不干预。

**应用路线因此调整为：先识别资源和选择具体能力；独立资源按证据允许并行，服务内部资源由原协议管理，只有共享冲突域才仲裁。** 不要求每个业务都实现`lease/act/observe`这一组方法，更不让OI新增Agent Session→资源分配表。r3的细锁方案保留为第三类的外部候选，不再代表链B全部形态。

### 4.2 业务会话、逻辑通道、底层连接不能混成一项

“不管理内容/ID”在这里落实为不识别工具参数、业务session或资源句柄；仍需OI自己的身份、目标、版本和通道标识，才能保证路由和授权。连接状态有生命周期并非业务耦合；反过来，即使把通信改成短请求，只要OI替调用者选择tab或维护任务账本，仍然耦合业务。

当前每次传输Open建立一对独立WSS数据腿，**不是每个Agent Session固定分配一个Channel/进程/设备**。原生调用方决定何时建立/关闭需要的字节流；同一传输可包含原协议允许的多次交互，一个业务会话也可能因原协议需要多条流。OI不猜消息边界，不替不同主体把业务流拼接到一个本地TCP连接；流与目标关系由公开传输契约决定。

“按负载开5个连接”可保留为未来**底层承载池**候选：逻辑Channel仍分别绑定授权目标/字节流，流级与总量预算、取消、关闭、故障影响必须明确；不能将5照抄为默认参数，更不能在某个承载连接断开后把旧字节无条件迁移重放。独立WSS简化首版协议但增加连接/TLS成本；池化节省连接但增加复用/公平/故障测试。首版保持现有WSS提案，按真实资源成本决定是否改选，不凭聊天或Python夹具宣布哪种更省。

### 4.3 “不干预内容”不代表没有故障范围

| 失败 | 应有边界 | 未承诺 |
| --- | --- | --- |
| B1业务进程失败/本路取消 | 对应暴露项/Channel失败及清理；B2在其他共同前提仍成立时可继续 | 服务B1/B2实际共用进程时的崩溃隔离 |
| 一条WSS数据腿故障 | 结束绑定通道；不改投B2或重放；其他通道不被无差别关闭 | 共享控制权威/许可失效时仍不断流 |
| OIC/OIS/宿主故障或许可失效 | 按当前控制/数据契约影响其关联流，明确范围与新建路径 | 独立socket等于独立进程/宿主/设备 |
| 共享桌面动作未知 | 外部执行方判定静止/隔离；OI报告传输原因 | 由断线或租约到期推出动作已停止 |

负载额度/有界排队降低资源耗尽传播风险，不提供独立运行环境。需要更强故障隔离时，可由外部部署者将OIC/能力放到不同进程或宿主，代价单独计入；OI不为此自动创建沙箱。原文“1C1G只放OIC”仍是待测目标，能力服务与接入端分别测量。

### 4.4 today例子约束的是产品取舍，不替OI接管业务

推荐的OI产品仍是独立的能力登记、发现、授权与跨网络接入；SDK/CLI可作为其接入形态。若只服务固定两台机器，原生SSH工具包装或一个业务SDK可能更便宜，不强迫引入完整OI；多环境权限/发现/主动出站需求出现时，才有能力网络增加管理面的价值。两者要比较实际接入与运维成本，而不是把“不做中间态”理解成必须做所有层。

today的“收集新闻”可由外部聚合服务调用多个来源，再把聚合接口登记成一个Exposure；它拥有数据源调度、去重、状态和结果。也可把各来源分别暴露，由业务消费者组合。OI不新增新闻Workload调度或内容管理对象。能力独立存在与可组合由外部实现和明确接口支持，OI保留可寻址/版本/授权关系；后续若要OI托管实例或编排，再另行改变已确认边界。

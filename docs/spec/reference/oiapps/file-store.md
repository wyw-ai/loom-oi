# File Store OIApp

**状态**　首版目标契约已封板，待实现。官方 File Store 的 `app.code` 为 `file-store`。运行包按普通 OIApp 交付，包含 `app.yaml` 和 Go worker，由部署方在选定 Host 的 OIC 加载。每个实例配置本机允许读写的目录、逻辑存储名、后端位置及其凭据引用。首版接通一个实际后端，具体部署选择见[首版目标](../../goals/service.md)。

## 路径与文件引用

| 值 | 解释 |
| --- | --- |
| `path`、`dest` | 执行 Action 的 Host 上，相对于该实例允许的源目录或目标目录的本地路径。生产文件的 App 和上传方需要访问同一份原件。 |
| `store_path`、`store_dir` | 所配置存储范围内的根相对路径和目录，可用于跨会话查找。存储路径与本机路径分别解释。 |
| `file_ref` | 包含 `store`、`file_id`、`size_bytes` 和 `sha256`。前两项定位一份不可变原件，后两项用于取回时校验。对象及还原引用所需的元数据保存在后端。 |

调用者须有权使用 Service 成员。worker 在实际读写时检查可信调用范围、实例允许的对象范围和本地目录。存储凭据由实例使用。

## 四项 Action

| Action | 契约 |
| --- | --- |
| `put_file(path, store_path?)` | 打开允许目录内的源文件，流式上传并计算字节数和 SHA-256。省略目标时生成唯一存储路径。默认对已占用路径报告冲突。完整原件与查询元数据写入且可查回后，返回实际 `store_path` 和 `file_ref`。后端异步受理时仍须确认写入完成。 |
| `list_directory(store_dir, limit?, cursor?)` | 按列举权限分页返回一层直接子项。每项有 `name`、`kind` 和 `store_path`，可以附已有的大小和修改时间。文件条目仅展示已完成且可见的对象。同次列举能取得引用时可带 `file_ref`，有后续页时返回 `next_cursor`。 |
| `lookup_file(store_path)` | 在指定存储范围内按完整路径精确定位，按读取权限返回对应 `file_ref`。目标路径缺失时报告未找到。 |
| `get_file(file_ref, dest)` | 下载到目标 Host 的允许目录。先写临时文件，校验长度和 SHA-256，再提交到目标位置并返回本机根相对路径。默认保留已有同名文件并报告冲突。 |

## 两台 Host 如何交接

前提是 A、B 的实例指向同一个实际存储范围。A 获准写入，B 获准读取对应对象。按目录浏览还需对该目录有列举权限。发布者可以将两个 Host 的不同成员选入同一个 [Service](../service.md)。

1. A 的生产者在本机生成 `captures/83.png`。Agent 调用固定到 A 的 `put_file`，传入该路径及 `shots/host-a/83.png`。上传成功后获得文件引用。
2. 有引用时，直接调用 B 的 `get_file`，例如取回到 `inbox/83.png`。只知道完整存储路径时先调用 B 的 `lookup_file`。只知道目录时先 `list_directory`，再通过选定条目的引用或完整路径取件。
3. B 校验原件并返回本地路径后，可把该路径交给能读取同一目录的其他 App。文件在存储中保留期间，B 可在 A 离线后取件。反向传递时交换两个实例的读写角色与授权。

文件原件沿 A、存储后端、B 传输。OIS 路由调用与回执，供 Agent 看图的 MCP 图像沿已有结果通道返回。多张截图并发时，通过上传回执或请求标识确认指定画面。

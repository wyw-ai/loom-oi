# Service 首版目标讨论

- 讨论标识为 `first-release`，主题为 `service`。文档父目录为 `docs/goal-shaping/`。
- 本轮范围是 Service 首版的用户目标、代表性使用过程和可观察的验收边界。状态为 2026-11-23 设计封板、讨论结束。
- 2026-11-19，在询问是否启动目标塑形后，用户回复“启动”。
- 工作分支为 `codex/service-goals`，起点为 main 的 `63c1db9`。新 worktree 中此前没有本主题的共识文件。既有行为以 beta 的架构和首版验收记录为参考。

## 2026-11-19 · 启动

依据用户提供的微信记录和设计讨论导出，已将用户在原讨论中明确的跨 App 选取、固定来源、Service 配置、MCP 发布和外部 API 接入写入 `current/service/design.md`，作为本轮起始共识。导出中的 workbench 和截图流程是讨论示例。

已提出以“工具可发现且可分别调用”和“Agent 能取得图片并回答用户”区分两个验收结果。用户的启动回复确认开展讨论，具体选择尚待答复。

## 2026-11-19 · 确认截图验收边界

用户确认首版须让 Agent 真正看到 Host A 此次的截图，并说出屏幕内容。截图用来验证端到端链路，Service 本身只负责组合和发布 Action。以上已同步到当前共识和本轮草稿。接下来需要明确 Agent 调用工具时是否要显式参与文件传递。

## 2026-11-20 · 核对 beta 实现

beta 从 `9f935d8` 快进至 `e40e35b7`。新增 Browser 与 Filesystem App，共用 `content.v1` 原生图像结果。beta 验证报告记录了从 MCP 返回的四个图像样本由模型读回随机批号。Browser 捕获专用 Chromium 页面；桌面截图仍是本主题的验收对象。此前提出的上传地址仅是一种交付方式。

当前 vMCP 的工具清单、固定绑定、访问范围、MCP 列举与调用构成 Service 的实现参照。这些结构在上一个 beta 中已经存在。本次扩展使跨 App 发布和原生图像交付有了具体验证。派发仍只支持已登记的 OIC 来源；外部 HTTP App 待设计。Browser 会话、profile 及 Filesystem 游标已使用可信消费身份与 vMCP 范围。以上是实现调查，提议在草稿中保留，尚未新增设计共识。

## 2026-11-20 · 整体架构推演

用户希望看清本次新增的领域模型与 OI 整体架构的关系。草稿将能力提供与接入、OIS 目录与发布配置、协议消费连成一条调用路径。建议先用 Service 中的成员关系表达固定来源引用；发布名称、契约和权限的归属尚未确认。另对照了 main 的 Workload 类型与 Coordination，区分实际运行的业务服务、发布工具清单与多步执行。

用户再次核对新版是否还有 vMCP，以及 Agent 调用 filesystem Action 的具体路径。按此前已定的模型，将未来口径明确为 Service 经 MCP 发布，并在草稿中用 read_file 串起发布、发现、选源与执行。beta 中 vMCP 标识和既有接口的迁移方式仍待实施设计。

用户认可 filesystem 链路，并要求梳理外部 file-store。草稿补充了经 OIS HTTP 适配器调用 create_upload 的对称示例，区分申请上传位置与实际发送文件；临时地址、文件引用与上传方仍是示例中的选择。

## 2026-11-21 · 讨论基线

用户明确本轮讨论 beta 的演进。此前把 main 长期蓝图带入领域模型的推演超出了范围，已从设计草稿移除。工作分支的创建起点仅是 Git 历史信息。

讨论不同 App 的演进。草稿提出让每种接入方式负责自己的执行配置，Service 统一选择具体来源的 Action。当前讨论 OIC 与外部 API，包托管仍是后续设想；独立的 App 定义和实例模型尚待确认。

按用户提出的 OI native 视角，补充两种来源如何进入同一 App/Action 目录，以及鉴权后如何按来源派发。共享能力描述、来源私有执行绑定和外部 HTTP 配置的分工是本轮候选，尚未确认最终格式。

用户询问外部 API 与 OI 谁适配谁。当前建议由 OIS 实现通用 HTTP 适配器、接入者配置映射、上游沿用自己的接口。

用户明确 OIS 提供的是 Function App。OIApp 的 Lua 脚本在 OIS 执行，每个函数对应一个 Action。外部文件服务由函数按需调用。先前提出的逐 Action 配置 HTTP 映射仅是已被替代的建议；这项纠正已同步到 current 和草稿。

用户询问本轮新增主线。草稿将 OIS 执行 Lua 函数与两类 Action 经 Service 统一发布串成一条交付路径，主线表述及 Function App 的验收建议待确认。

用户询问由 file-store Lua 上传时二进制如何抵达函数。候选方案是 OIS 对一次截图结果发放短期引用，由调用方显式传入另一项上传 Action，Lua 经宿主 HTTP 发送。未把文件引用或这条路径设为已确认要求。

## 2026-11-22 · App 之间如何联用能力

用户质疑把图片跨请求暂存在 OIS 的复杂度，要求重审 App 联动方式。先前的短期引用提议假设了两次分离的 Agent 调用。本轮候选改为 Function App 在一次调用中使用已绑定 Action 的结果，由 Lua 表达业务顺序；若只需给大文件安排去向，可传上传目标、由源端直传。两者的数据路径、执行责任及适用条件已写入草稿，等待用户判断。

用户提出 OIC 上的 OIApp 也应考虑相同的联动能力，两类 App 的实现应采用类似机制或协议。草稿把推荐的能力上移到共同宿主契约，补入 worker 在执行期间经 OIC 请求子调用的路径，以及截图原件由 Host A 直传的例子。Lua 接口形式、跨进程消息和具体授权绑定仍待确认。

用户提出将普通 OIC 随 OIS 同机部署、统一采用 OIApp，以缩小这次改动。beta 首版验收已有 Linux 上 OIS、OIC、Bash 同机的实例。作为候选，可用遵守现有 worker 协议的 Lua 执行器承载函数；服务端远程提交脚本及 App 内部子调用均需各自补齐。当前等待确认希望提供的安装、上线体验。

用户明确本轮不需要 Lua，直接走 beta 原有 OIApp 链路。此前关于 OIS 内执行 Function App 和由同机 OIC 承载通用 Lua worker 的两种方案均被本决定替代。服务端的 file-store 可作为普通 OIApp 由同机 OIC 加载。current 与活跃草稿已按此同步；Service 发布、Host A 的看图验收继续有效。worker 主动调用其他 App 是否进入首版仍待讨论。

用户将 file-store 明确为本次新增的官方内置 App，并要求说明目标模型、API、具体实现和联动。已同步其官方 OIApp 身份。草稿补充了 Service 管理及 beta 兼容接口、file-store 的上传授权与按权读回、Agent 串联和 worker 主动子调用两条路径。具体接口名、后端选择与子调用是否进入首版属于建议。

用户进一步明确 file-store 与 Browser、Filesystem 的部署地位相同，由选定 Host 的 OIC 加载。此前默认使用 OIS 所在机器的示例已从共识和活跃草稿移除。用户提出自研文件服务、OSS、COS、NAS 和 AList，后端选型仍开放。

本轮建议优先复用可用存储。截图与 file-store 能读到同一受限目录时，可以通过普通 Action 传根相对路径，用 file-store 的凭据上传到 AList 的可写 WebDAV 挂载，或使用已挂载的 NAS。若源和 file-store 分居两台 Host 且没有共享目录，OSS/COS 的限时上传目标可以让源端直传。草稿中两种方案均属候选。共识基线为普通 Host OIApp、Service 组合发布、Agent 读图描述 Host A 当次屏幕。

## 2026-11-23 · 上传与跨 Host 文件传递

沿用 File Store（`file-store`）讨论官方 App。用户要求串起目标领域模型、API、本次上传和未来两台 Host 间的文件传递。草稿建议用对称的 `put_file` / `get_file` 和有存储范围的文件引用。本地路径只在约定根内使用，共用同一存储的授权实例可以独立解析引用。建议把 Host A 的原件上传、读回到另一处，再复用现有 `filesystem.view_image` 做看图验收。B 的独立下载可以沿用同一契约，存储互不相通的场景另议限时直传。后端、字段及首版是否加入通用下载均为提议。已确认的验收与 Service 职责未变。

用户提出按路径查文件。草稿把 Host 本地源路径与存储路径分别表达，建议上传时可指定并返回 `store_path`，在后续会话或另一台有权读取同一存储的 Host 上用 `lookup_file(store_path)` 找回 `file_ref`。若已有文件引用，仍可直接下载。具体 Action、命名路径与冲突处理为候选。

用户补充 B 只知道共享目录、未知文件名的场景。草稿建议 File Store 提供普通 `list_directory` Action，分页返回可见的直接子项，再通过选中的存储路径或文件引用取回。目录中多张截图的请求归属须靠上传回执或约定标识判断。目录列举和返回字段仍为候选。

按用户要求将四项文件能力、Service 接口及首版交付清单整理在同一份草稿里。配置迁移覆盖 beta 首次导入的 YAML 和已运行实例的持久 JSON。共用存储的双 Host 传递可以复用同一组 Action，独立存储直传属于后续场景。此次整理用于讨论，后端与具体 API 尚未定稿。

## 2026-11-23 · 封板与归档

用户确认本轮可以封板，并要求归档目标、整理规范和推送。已采纳 Service 的领域边界与发布接口、官方普通 OIApp File Store 的四项 Action、文件引用与共享存储的跨 Host 交接，以及以 Agent 实际描述 Host A 当次桌面为准的验收路径。设计以 beta `e40e35b7` 为实现基线。

首验使用哪个真实存储后端、旧管理接口的兼容期限仍待实施时确定。不同存储之间的限时直传留作后续。此前讨论的 Lua、OIS 暂存和 worker 子调用留在历史笔记中。封板完成的是目标设计，代码交付和端到端验收待执行。

# 文件传输：OIS 原生 API/MCP 与在线中转（修订提案）

**本版暂缓。** 控制端与受控端之间、两台受控端之间的原件传输均留作后续评审。本文仅保留候选架构。本版两项图像预览在各自的 Action 响应里返回。

用户希望控制端与受控端双向传输、受控端 A 与 B 互传；消费端直接使用 OIS API/MCP，优先不要 OIS 存储文件。此前“本地专用 CLI/SDK 协调分块”的建议已撤回。本稿是按此方向重新提出的选型，不是用户已经批准的协议或已有能力。

## 1. 消费端只看到三个操作

| 意图 | HTTP 外观（示意） | MCP 外观（示意） |
| --- | --- | --- |
| 控制端 → B | 对有权的目标发一次 PUT，body 为文件字节；成功回执含相对路径、大小和 SHA-256 | 准备一次限时上传入口；拥有本地文件的客户端用普通 HTTP PUT，或用户通过 OIS 选择文件的薄页面上传 |
| A → 控制端 | 对有权的文件发一次 GET，响应为原始字节与下载文件名 | 准备短期下载入口，客户端或用户打开链接即可接收文件 |
| A → B | POST 一次 copy 请求，含两个具名端点及根内相对路径；返回任务 ID，可查状态或取消 | 一个 copy_file 工具调用，同样返回任务 ID、最终结果或错误；模型与控制端不接收正文 |

不强制安装工具、编写分块逻辑、提供本机公网服务或把 Base64 经过模型。也不能承诺纯远端 MCP 服务仅凭本地路径便能打开客户端文件；上传一份仅存在于用户电脑的文件，总要有用户选文件、客户端发送字节或已有附件集成中的一种。若提供选择文件页面，它是 OIS 面向用户的小入口，仍直接转发 HTTP，不增加文件库。GET 成功只指服务端已发送，实际“已保存到本机”由客户端确认；下载链接不等于永久附件。短链绑定一次操作，按凭据模式重验范围；供浏览器直接打开而不能带 Authorization 的链接必须明确为短期、一次使用的持有者凭证，只授权指定对象/方向，不在日志中记录密钥。

## 2. 一条在线管道，三种端点组合

同一传输协调器配对一个 reader 和一个 writer：上传时 reader 是外部 HTTP body；下载时 writer 是外部 HTTP response；跨端复制时两头都是 OIC。OIS 保存有界内存缓冲和小量任务元数据，不建立原文件、临时大文件或持久下载 URL；反向代理、表单解析及日志同样不可隐式把正文落盘。提供方预配置命名端点，例如 reports-linux、reports-windows，各自固定到 OIC、工作根和读写方向；vMCP 只暴露获准的端点和操作。调用方不能填任意 channel、主机、URL 或根目录。跨端复制是 OIS 新增的一类显式操作，不把现有固定 Tool 调用改为动态选路。

推荐新增可独立关闭的通用传输能力，和业务 Action 分开。控制面使用现有 OIC→OIS WebSocket：协商能力、准备 source/sink、发短期单用途票据、接收发布结果；不向旧端发送新消息。数据面在同一 OIS 地址下新增独立 HTTPS 路由；由 OIC 按已配置的 OIS 地址主动 POST（作为来源发字节）或 GET（作为目标取字节）。不向 OIC 开公网端口，不需要两台 OIC 互相可达，也不把大文件塞进现有 JSONL/WS。两条到 OIS 的连接用途不同，不是抢占同一个 channel 的第二条 WS。可部署在同一域名和服务进程，需独立设置慢上传/下载超时与反向代理流式策略。现有管理/调用接口配置不自动开放传输；数据面验证 channel 身份、工作世代和单次票据，并要求认证和加密。

以 A→B 为例：OIS 核对同一调用身份在同一 vMCP 对 A 的导出权和对 B 的导入权；A/B 各自核对本机根和权限。B 先预留额度并打开同卷私有暂存文件，A 打开源的受限普通文件；双方准备完成才泵送字节。OIS 以有界缓冲复制，B 慢则 A 随之减速；不做无界排队。A 与 B 独立计算大小和 SHA-256，A 完成后通过控制面给出源摘要及可检测的源文件变化；只有 B 完整接收、比对成功并无覆盖发布后，OIS 才报告成功。针对 GET，首版可预读源文件计算长度/摘要后回卷或使用受控端限额内的稳定副本，以便在 HTTP 响应头给出可校验的长度/摘要；不能假定发头后还能用新状态码报告读取失败。用户文件在端点，OIS 流经并能看到正文，不宣称端到端加密。OIC 的文件读写用根句柄、限额及临时发布；尽量复用 Filesystem 的受限 I/O 设计，避免同时维护两套不一致的路径语义。

## 3. 范围、代价与恢复

- 首版：在线、单个普通文件、固定授权根、默认禁止覆盖、限制文件大小/并发/缓冲和等待期限。建议先做单 OIS 实例；MCP 慢任务即刻返回 ID，复制不依赖原 MCP 请求保持连接。临时任务状态存内存并有 TTL，首版不承诺多副本接力、重启恢复、离线投递、目录同步或断点续传。
- 中途断开：已确认未发布时由 B 清理暂存，再由消费者整件重试。提交已发出但回执丢失时返回 unknown，不能盲目重复；用客户端请求键绑定方向、来源、目标，必要时查询 B 的有限发布记录/实际文件摘要。若连元数据都已过期，请求结果不作成功承诺；不自动删除已发布目标。控制端中断 GET 只表示下载可能不完整。
- 开发成本为中等：已有 OIS 鉴权、固定通道、OIC 出站和 HTTP/TLS 入口可复用；新的工作是端点绑定/授权、协调状态机、二进制 HTTP 配对、原子或无覆盖发布、错误报告、两平台清理和真实压测。原版 [invoke](../../../../../internal/ois/invoke.go) 一调用一结果，[协议](../../../../../internal/protocol/protocol.go) 的 1 MiB 限额、[OIS 连接](../../../../../internal/ois/connection.go)的串行 JSON 写和[现有 HTTP 期限](../../../../../cmd/ois/main.go)不适合原样承载长文件，单纯放大帧没有解决问题。
- 运行成本主要是中心带宽而非存储。复制 N 字节的文件时，OIS 收 N、发 N（不含协议开销）；内存应随并发传输数与每流缓冲增长，而非随文件大小增长。写入端会临时占一份文件空间。在线双方之一不可达就不能交付。只有离线取件、源端断开后永久下载或长期分发成为必要条件时，再选持久中转/对象存储；仅想跨重启查询任务，可以只持久化元数据。
- 替代方案：OIS 在服务端串行调用内部分块 handler 可以快速做有大小上限的原型，对外 API 不变；但 Base64、往返延迟、宿主调用缓存、两端调用数是实在成本。长期开启优先选择独立 HTTP 数据面。直接 OIC 对 OIC 虽节约中心流量，却引入可达性、地址发现和证书配置；不作首版默认。

## 4. 与两个 App 的关系和通过标准

同一受控机内，专用工作根即可打通 Browser 下载 CSV → Filesystem 带 revision 编辑 → Browser 上传，不经过 OIS 传输服务。跨机器时只复制配置根内的完整文件；不向 Browser 新增“任意 URL 下载并转发”，也不向 7 个 Filesystem Action 增加模型可见的分块接口。传输是新平台能力，应独立排期，不阻塞已有两个 App 的基本功能开发。

验收分三步：普通 HTTP 客户端上传/下载，比较原始字节；一个 MCP 操作把 A 的二进制文件复制到 B，并由 B 独立核对、不经控制端中转；模拟目标离线、同名冲突、磁盘满、慢接收端、任一端掉线以及发布后丢回执，验证错误语义、内存上界、OIS 无正文落盘与普通调用仍可响应。成功回执不是在源端读完或中心读完时生成。

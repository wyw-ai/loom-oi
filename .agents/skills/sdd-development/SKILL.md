# SDD Development

先读 [AGENTS](../../../AGENTS.md)、[开发流程规范](../../../docs/sdd/development-workflow.md)和[结构规范](../../../docs/structure.md)。仅在讨论或方案未收束时，结合 [Discussion SDD](../discussion-sdd/SKILL.md)完成求解与确认；不要借实施任务重新批准整个项目。

## 执行步骤

1. **定位任务**：检查分支、目标分支、基线 SHA、工作区差异、最新相关规格及原始确认。将请求归到一个独立可验收目标；两个目标拆为两个任务，不能只改任务名将它们包装在一起。保留他人修改。
2. **先写文档**：在 `spec/<任务ID>-<简述>/README.md` 使用[模板](../../../spec/_template/README.md)，写目标/非目标、需求验收、方案影响、实施子步骤、确认和验证计划。按结构规范同步长期规格，引用原始 DISC/Issue；不复制整套设计，不将待实现行为写成已可用。
3. **核对完整确认**：回读人类原始指令/评论及其准确版本范围。明确完整的用户指令可直接作为确认；部分确认、AI 摘要、检查器通过、Issue 关闭不能覆盖未决项。未确认则准备可评审方案并指出具体未决项，停在建 feature 和产品实现之前；本任务之外的无关未决项不阻塞。
4. **开单任务分支并先推文档**：完整确认后从约定目标分支的最新提交创建 `feature/<任务ID>-<简述>`，第一笔仅提交本任务 spec、必要长期文档及导航，推送并回读后才开始产品代码。已有分支仅在绑定同一任务且未混入其他目标时继续使用。遇到混入任务，先隔离，禁止丢弃工作或带入同一 MR。
5. **实现和测试**：按确认方案实现同一目标的子步骤；新独立需求另记任务。实质方案变化先更新文档并重新确认受影响范围。用预定工具运行单元测试，核验全体受管自有源码和各变更模块的行/语句覆盖率分别至少 95%，包含未执行源码，保留分子/分母及可读取报告。不得混用集成覆盖率、忽略业务代码、伪造报告或靠无断言测试达标。代码任务没有测试设施时先补齐。
6. **检查文档与代码**：在最终 diff 上逐项核对需求、API/CLI、配置默认值、权限/状态/失败、数据迁移、部署命令、示例、图和导航；填写文档→实现→验证矩阵。修代码或在已确认范围内修文档；无法确定则回到确认，不静默改需求适配错误代码。
7. **核验最终版本**：运行适用的结构/SDD记录检查、任务链接检查、测试/覆盖率和实验门槛。记录源码 SHA、目标分支基线、环境、命令、报告和一致性结论；代码或合并结果改变后重验。检查器通过不能代替语义核对。纯文档/技能任务只有在 diff 确认无可执行/构建/运行行为改变时才可记录覆盖率不适用，不能报 100%。
8. **提交 MR**：全部出口条件满足后，使用 [MR 模板](../../../.github/pull_request_template.md)，只关联一个任务。逐项链接完整确认、先推文档的提交、覆盖率报告、一致性矩阵及剩余风险；任何阻塞未解决都不创建 MR，包括草稿。仅提交 MR 不自动合并、发布或部署。

## 交付表述

报告唯一任务、分支、实际文档/代码变更、真实测试与覆盖率、文档一致性结果及远端保存状态。未运行、失败、未配置、待确认分别如实描述；不要把规范写好说成 CI 已启用，不把本地提交说成已推送。

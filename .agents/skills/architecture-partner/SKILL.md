# Architecture Partner

读取唯一的完整工作 prompt：[Architecture Partner](../../../docs/prompts/architecture-partner.md)。本技能是项目执行入口，该 prompt 维护完整角色契约，避免复制成两套角色。

已有完整采用的开发任务转由[SDD Development](../sdd-development/SKILL.md)持续执行；不要把普通修复/测试重新解释为需确认的架构脑暴。发生实质产品取舍才回到本流程，并限制等待范围。

## 执行顺序

1. 确认主题、当前分支与授权，先读[项目理念](../../../docs/concept/loom-oi.md)与[项目收束规则](../../../docs/sdd/README.md#project-convergence)，再读取 [KB 入口](../../../kb/README.md)、当前架构、相关 Issue 和评论。缺少信息时继续可独立开展的推演，明确假设。
2. 讨论输入同时使用[Discussion SDD](../discussion-sdd/SKILL.md)：同源去重、创建DISC记录，每轮必须追加阶段评论或必要的新/子Issue，记录具体方案与范围；没有技术变化也提交保持理由，不能只写文档。蒸馏真实来源与确认范围。先用一个端到端场景建立产品边界、对象、交互、信任、状态/失败和部署成本的共同基线，明确假设。
3. 将问题挂到loom-oi的用户结果和共同契约，识别能改变下游负载/信任/失败边界的研究变量；比较完整架构候选，再写专项解法。路径、存储或部署只是机制，不能用组件方案反向定义产品。推荐附“来源→约束→推论→机制→取舍/反证→下游影响”；旧单结构和旧 AI 推荐不是证据。
4. 先按[结构规范](../../../docs/structure.md)定位仓库现行规格；Issue按[追加规则](../../../docs/issue-management.md#append-only)保留已发布正文/评论，用新阶段承接变化。新研究先查[kb/lineage](../../../kb/lineage.md)旧尝试、失败依据与条件差异；发现疑似重走旧路，按[轻量门控](../../../docs/issue-management.md#revisit-gate)提交针对性确认Issue，不建设另一套工具。按独立决策目标整理Issue；不能独立收敛的专项合并讨论、保留来源和反例、不重复计分。获用户清理授权时，已定且无分歧的选择按收束规则关闭，剩余实验转已有验证单。可并行推演分支，只有依赖选择的规格冻结等待决定。
5. 当轮用正常场景和整体反例检验机制；写清代价、可逆性、证据缺口和最小验证。语言选型按实际功能/部署/维护条件推导。
6. 逐条跟进人类回复：准确确认范围、未确认项、影响链和落实结果；追加Issue阶段并同步当前架构与KB。读最新状态后再写，保留包括AI自己的所有已发评论；同步后按[评论回复规范](../../../docs/issue-management.md#comment-replies)在原Issue回应并回读，让用户直接核对改动，不能仅更新正文。
7. 需要实验时调用 [架构 Evidence Lab](../architecture-evidence-lab/SKILL.md)，按其规约验证并保留原始数据；实验后自动结合KB和整体方案收敛结论，不等待再次指令；沿 [产物联动表](../../../docs/architecture-artifacts.md) 更新图、契约和验收。
8. 完成项目收束：逐项说明本轮保持/改变的项目承诺、共同不变量、端到端体验和总成本，更新概念/架构的唯一正文或说明无影响。再检查跨单矛盾和过时验收，记录实际协作缺陷，按需修改 prompt/模板并验证。不要用字段、篇幅、方案数量代替设计质量。

## 按需读取

- Issue 工作：[管理规范](../../../docs/issue-management.md)、[当前规划](../../../docs/alpha-issues.md)、[模板](../../../.github/ISSUE_TEMPLATE/problem.md)。
- alpha 设计：[讨论蒸馏](../../../docs/alpha-discussion.md)、[当前架构](../../../docs/architecture/alpha-v0.7.md)、[具体方案](../../../docs/proposals/alpha-solution-design.md)。
- 源码/协议事实：[证据台账](../../../kb/evidence.md)的固定版本及来源；按问题读取原件，不只引用摘要。

## 输出自检

- 若只有问题、研究计划和验收清单，没有具体机制、推荐和反例，继续求解。按[内容评审](../discussion-sdd/references/content-review.md)把主要讨论线程逐一对照Issue正文；正文不能只留治理流程并让读者跨链接自行拼方案。未来场景即使不进首版，也推导其对当前接口的要求。
- 做双向追踪：向下说明每个模块为何必要，向上证明局部机制组合后仍保持目标、权限、失败与资源边界；“新增链接/整体图”本身不证明整体成立。
- 最后的确认项也要反映共同主问题：若路径改变负载前提，先比较含路径/失败语义/部署条件的完整候选，不能把研究写全后又只让人选择拆不拆进程；研究准备不以候选已被采用为前置。
- 推荐应说明牺牲什么、何时不适用、什么证据会推翻它。
- Issue 应能独立理解，含上游条件、实质机制、证据链和反例；所属主线负责共同决策，详细机制回链仓库。
- 检查全部下游：确认“暂不集成”后不得残留集成验收；选透明通道后不得保留业务成功/回滚保证。
- 已授权主题内可以更新成熟问题与方案；新方向、未成熟构想或扩大范围才先列候选。
- 不以文档证明实现，以模型推演证明实测，或以 AI 推荐证明人类同意。本技能不增加合并、关闭、分派或生产实施权限。

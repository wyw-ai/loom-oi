# loom-oi

让脚本、应用和 Agent 在明确权限和失败边界内，发现并连接分散环境中的受控能力。

能力提供方继续拥有自己的服务、设备和业务逻辑。loom-oi 负责把获准的消费者连接到准确的目标，提供统一的发现、授权、接入和传输诊断。

## 一个具体场景

在一台主机上部署 OIC，登记该主机已有的 SSH 服务。消费者通过 OIS 发现获准目标，用 `oi` 建立通道，再使用原生 SSH 连接并执行 Bash 任务。

SSH 继续负责登录身份、命令权限和执行结果。OIC 不安装 SSH 服务，不提供任意命令执行接口，也不因为暴露一个服务就开放整台机器。

## 组成

| 组件 | 职责 |
| --- | --- |
| **OIS** | 维护目录与访问策略，协调连接，并承担首版可信中继 |
| **OIC** | 在受控环境主动出站接入，登记允许暴露的目标，执行本地约束并转发连接 |
| **oi** | 消费侧命令行：发现目标、建立本地转发或标准输入输出通道；也提供管理命令 |

首版使用 Go，采用单实例 OIS 和中继路径；存储可选择 PostgreSQL 或 SQLite。loom-oi 独立于 Loom，未来集成由上层适配完成。

## 当前状态与近期目标

OIS、OIC、oi 以及授权、双后端存储、观测与通道机制已有实现，**完整发布验收尚未完成**。历史版本的通过结果不代表当前版本已经具备全部保证。

近期交付目标：

1. 完成“消费者 → OIS → OIC → 已有 SSH/Bash”的实际使用验证。
2. 验证当前版本的权限、目标绑定、断连、取消、存储恢复和资源边界。
3. 给出基于实测的支持范围和使用说明，再判断首版是否可以交付。

直连、多路径、存量连接迁移和高可用不属于当前已交付能力。OI 连接恢复不代表业务任务恢复，也不自动重试可能已经执行的操作。
